# DO duration 暴涨排查记录（2026-10-26 ~ 11-05）

一次「请求数只涨 8%，duration 却翻 6 倍」的完整排查，期间走过两段弯路，最终定位到
**一条永久停在 CLOSING 状态的 WebSocket**：它让对象拿不到 hibernation 资格，撑满 15 分钟后
才被驱逐，期间按墙钟计 duration（handler 实际只忙 1%）。修复后用量从 100%+ 降到 13.5%。

> 根因修复只要一行：**重建阶段不再对落选连接调用 `close(4001)`**（见第七节）。
> 但找到它花了 10 天，因为前 6 天的证据都指向"平台侧"。本文把弯路一并留下——
> 那些错误结论比正确结论更容易被复述。

## 一、现象

| 指标 | 10-25（正常） | 10-26（异常） | 变化 |
|---|---|---|---|
| TerminalDO 请求 | 28,605 | 30,894 | +8% |
| 总 duration | 2,091 GB-s/天 | 13,241 GB-s/天 | **+533%** |
| 单请求折算驻留 | 0.55 秒 | 4.0 秒 | ×7 |
| 免费额度占用 | 16% | **102%（已超限）** | — |

关键观察：

1. **请求数与 duration 脱钩** —— 流量没涨，单条变贵。
2. **四个分片同步恶化** —— 排除单对象卡死。
3. **拐点落在 10-26 09:00 UTC，而该时段没有任何部署** —— 排除代码变更。
4. **会自行恢复，且在不同分片之间转移** —— 见下表。

按分片看（秒/请求），同一 version、同一小时：

```
小时    2f7b     33ca     a0f9     e8bb
01:00   1.55    12.35     0.69    13.35
05:00   0.21     0.14     2.96     0.14   ← a0f9 和 e8bb 对调了
09:00   0.19     0.14     3.89     0.14
```

一条都跑同样的代码，差 100 倍，且差异会在对象之间跳。

## 二、换算口径（重要）

GraphQL 的 `duration` 单位是 **GB-s**（128MB 实例 × 墙钟秒 / 1GB），除以请求数得到
「单请求折算驻留」：

```
驻留秒 = duration ÷ requests × 7.8125
```

再折算「对象每小时存活占比」更直观：

```
存活占比 = 驻留秒 × 该小时请求数 ÷ 3600
```

实测：

| 分片 | 小时 | 存活占比 |
|---|---|---|
| a0f991（健康） | 22:00 | **1.4%** |
| e8bbb6（异常） | 22:00 | **77.9%** |

健康对象每小时只活 52 秒（1.4%），异常对象活 2,803 秒（78%）。

## 三、机制：non-hibernateable（这是症状层，触发点见第七节）

> 小结：本节解释「为什么计费高」——对象停在 `non-hibernateable` 状态，按墙钟计费。
> 但**它为什么会停在这个状态**，直到第七节才查清：一条永久 CLOSING 的 WebSocket。
> 如果只想看结论，可直接跳到第七节。

官方 `Lifecycle of a Durable Object` 定义三种空闲状态：

| 状态 | 计费 |
|---|---|
| Idle, in-memory **hibernateable** | 10 秒后 hibernate，**窗口内也不计费** |
| Idle, in-memory **non-hibernateable** | **计费**，直到 70–140 秒后被 evict |
| Hibernated / Inactive | 不计费 |

hibernation 需要**同时**满足四条：

1. 无 `setTimeout` / `setInterval`
2. 无未完成 I/O / `waitUntil` Promise / 开放出站连接
3. 未使用标准 WebSocket API（必须走 `acceptWebSocket` + `webSocketMessage`）
4. **没有正在处理的请求/事件**（`webSocketMessage` 返回的 Promise 未 settle）

78% 这个数字正好是「non-hibernateable + evict 兜底」的特征值：

```
间隙占比 = 唤醒等待 / evict 周期 ≈ 20 / (70~140) ≈ 14%~29%
存活占比 = 71%~86%        ← 实测 78%、85%，落在区间内
```

**若真是永久卡死，存活占比会是 100%。** 实际不到，说明 evict 还在工作。

## 四、代码侧的挂起点

排查时发现上报热路径上有三处**没有超时**的跨 DO `fetch`，任一处挂住都会让
`webSocketMessage` 不返回，从而违反第 4 条判据：

| 位置 | 下游 | 修复 |
|---|---|---|
| `report.js` → MetricsDO `/report` | 含告警 webhook（`sendWebhook` 自身无超时） | `AbortSignal.timeout(2000)` |
| `do-terminal.js` 握手 → PanelDO `/viewers` | 读内存计数器（1–3ms） | `AbortSignal.timeout(1000)` |
| `do-terminal.js` 兜底 → PanelDO `/viewers` | 同上 | `AbortSignal.timeout(1000)` |

另外把 5 处告警 webhook 从 `await` 改为 `state.waitUntil()` 托管（`bgRun`）：
webhook 慢不再阻塞 `/report` 返回。`sendWebhookRaw` 自身加 5s 超时。

同时把 DO 内原有的 fire-and-forget 全部 await 化（`broadcastViewers`、`setPush`、
`resendWaitingUploads`、`settleJobsOnDisconnect`、各处 `storage.delete`），并删掉
exec 探活的 1 秒 `setTimeout`（改为「上报顺风车 probe + 无记录乐观放行」）。

## 五、可复用的排查手段

### 1. 按分片看，不要看总量

总量会把「一片 15 秒、三片 0.2 秒」平均成「1 秒」，掩盖问题。必须
`dimensions { datetimeHour objectId }` 拆开。

### 2. 换算成「存活占比」而不是「单条成本」

单条成本会随请求量变化；存活占比直接反映“对象有没有休眠”。

### 3. `[stat]` 快照：唯一能直接证明「对象没休眠」的手段

`TerminalDO` 每存活满 60 秒输出一行。**不要用「跨整点」触发**——实例寿命远短于 1 小时，
永远跨不过去，实测部署后一整小时一条都没有：

```
[stat] {"age_s":721,"win_s":60,"msg":4,"req":3,"cold":0,"in_ms":1129,
        "fwd_ms":0,"fwd_to":0,"alrm":0,"refire":0,"send":4,"send_fail":0,
        "inflight":0,"close_super":1,"close_auth":0,"close_sess":2,
        "sess":0,"intv":3,"pend":0,"socks":4,"ctrl":4,"user":0,"other":0,
        "ws_open":3,"ws_other":1,
        "ws_states":"control:1*,control:2:sess@2140,control:1,control:1",
        "alarm_s":null}
```

| 字段 | 含义 | 异常值 |
|---|---|---|
| `age_s` | 本实例已存活秒数 | 持续增长且不断输出 = 从未休眠 |
| `cold` | 窗口内冷启动帧数 | ≈msg：每条都重建（正常）；0：从未重建 |
| `in_ms` | handler 内部耗时之和 | 远小于计费驻留 = 大头是空闲计费 |
| `inflight` | 未 settle 的出站 I/O 数 | 长期 ≥1 = 卡在某个 fetch/D1 |
| `alrm` / `refire` | alarm 次数 / 空转次数 | 上千 = alarm 自激 |
| `ws_other` | 非 OPEN 的 socket 数 | **长期 >0 = 连接泄漏** |
| `ws_states` | 逐条 `role:readyState` | `*` = 当前 `agents` 登记者；`:tag@N` = 被哪条路径、N 秒前关闭 |

**没有 `[stat]` 本身就是结论**：没有任何实例活过 60 秒，即全部正常休眠。

### 4. `[slow-report]` 的盲区

`[slow-report]` 的埋点在 `handleReport` **返回之后**才执行，所以**挂起时不会输出**。
「0 条 slow 日志」既可能是"真不慢"，也可能是"挂了没走完"。

`[slow-msg]` 补上了这个盲区：它包在 `webSocketMessage` 外层，对**所有类型**消息计时
（report / pong / exec_result / 二进制），慢消息一定会留下类型与总耗时。
实测抓到过一条：`{"type":"report","role":"control","ms":1059,"cold":1}`，
说明「有 2 秒的 ws-message 却没有任何 slow 日志」时，原因往往是**它不是 report**，
或 `serverId` 取到 0（旧实现会跳过 logSlow）。

### 5. `--durable-objects-code-update-mode immediate`

Cloudflare 自 2026-10-30 起默认 **deferred**：部署后活跃对象可继续跑旧代码最多 300 秒，
等它 hibernate 才切新版。**实例一旦 non-hibernateable，靠部署重启不掉它。**

```bash
npx wrangler deploy --durable-objects-code-update-mode immediate
```

本项目已在 `wrangler.toml` 固化为 `[durable_objects.code_update_strategy] mode = "immediate"`。
**注意**：`immediate` 只是「能重启」，不是「修好了」。10-31 与 11-04 两次重启都把分片打回
基线，但分别在约 2 天后与 25 分钟后复发——真正的原因见第七节（重建期 close 制造的永久
CLOSING socket）。现在它退化为一项便利：需要清状态时不必等 5 分钟。

## 七、真正的根因：永久 CLOSING 的 WebSocket

### 现象链

```
[stat] ws_states = "control:1,control:2,control:1,control:1"   （6/6 快照一致）
socks=4  ws_open=3  ws_other=1  intv=3   send_fail=0  inflight=0  alrm=0

age_s: 120 → 240 → 361 → 481 → 601 → 721 …（持续增长，同一实例）
多次观测的寿命上限：864 / 894 / 920 秒 ≈ 15 分钟
其余三个分片一条 [stat] 都没有（活不过 60 秒）→ 同代码 A/B 对照
```

### 机制

1. `rebuildIndex` 在实例**刚被唤醒**时，对同 serverId 的落选连接调用 `close(4001, 'superseded on rebuild')`；
2. 此刻落选那条的对端往往已经消失，`close()` 发出关闭帧后**永远等不到回执**；
3. socket 停在 `readyState=2`（CLOSING）挂在对象上——`getWebSockets()` 依然返回它；
4. **一条 CLOSING 连接就足以让对象拿不到 hibernation 资格**，运行时于是把它当作「还有操作
   没做完」，撑满 ~15 分钟才驱逐，期间按墙钟计 duration（handler 只忙 1%）；
5. 驱逐后新实例重建时又执行第 1 步 → 再制造一条 → **永久自锁**；
6. 只有 `immediate` 重启会重置对象上的 socket 集合，所以它能"治好"，但只是暂时的。

这也解释了两个此前无法解释的现象：**为什么某个分片一旦变坏就几小时不恢复**，以及
**为什么"重启就好、过一阵又坏"**。

### 修复

| 提交 | 内容 |
|---|---|
| `1715be7` | 重建阶段**只登记 ts 最大者，不 close 落选连接**（收敛性由 `agents` 保证） |
| `76719f7` | 入站刷新加身份守卫：`curDead \|\| cur === ws \|\| wsAttTs(ws) >= wsAttTs(cur)` |
| `d3b07ed` | 重建的旧格式（纯字符串）分支加同一判据，避免新旧混跑时覆盖新格式胜者 |

`76719f7` 那条守卫不能用审查最初建议的「仅 `ts >=`」：半开死连接的 ts 更大，真正活着的
那条 ts 更小，纯 ts 守卫会拒绝活连接、索引继续指向死连接（exec 直接打不通）。必须加上
`curDead`（当前登记者非 OPEN 时允许接管）这一支。

保留握手里的 `prevAgent.close(4001)`：那是「新连接顶替旧连接」的正常路径，对端通常还活着、
会回 close 帧。实测 90 分钟内该路径反复执行（请求量 180–190/小时，其中约 60 来自握手），
却没有再出现 `control:2`。

```

之后 90 分钟：日志共 2 条（[slow-msg] 1、[slow-report] 1），[stat] 0 条
```

必然又出现一条 `[stat]`。期间对象被反复冷启动（`cold=1` 的日志为证）却零输出，说明
重建已不再制造 CLOSING。

### 判据（复发时按这个顺序看，不要再跳到「平台侧」结论）

**第 0 步永远是「先排除正常快采」**——`[stat]` 出现不等于复发，见下节。

| 观察 | 结论 | 动作 |
|---|---|---|
| 出现 `[stat]` 且 `age_s` 持续增长 | 对象没休眠 | **先做「正常快采」排除**，再往下看 |
| `ws_other > 0` / `ws_states` 含 `:2` | 有连接卡在 CLOSING | 看 `:tag@N` 后缀定位来源 |
| `ws_states` 含 `control:2:super@N` | 握手顶替那次 `close(4001)` | 改成「只换引用不 close」 |
| `ws_states` 含 `control:2:sess@N` / `:auth@N` | 会话清理 / 鉴权路径 | 查对应 close 调用点 |
| `control:2` 无 `cx` 后缀 | **不是我们关的**（对端断开后运行时置为 CLOSING） | 另查 |
| `inflight >= 1` 长期不变 | 卡在某个 fetch/D1 | 顺着 4 个 `tracked()` 入口定位 |
| `alrm` 上千 / `refire > 0` | alarm 自激 | 查 `setAlarm` 的入参 |
| 以上全正常但仍高 | 才考虑平台侧 | 用下面的素材开工单 |

### 正常快采 vs 复发：怎么区分

**有人开着面板时，`[stat]` 一定会出现，这不是故障。** 面板打开后上报切到快采
`REPORT_FAST_INTERVAL_S = 5`，对象每 5 秒被唤醒一次，永远凑不出 hibernation 需要的
10 秒空闲，于是 `age_s` 一路增长、`[stat]` 每分钟一条。这是设计使然。

实测（2026-11-05 14:48–14:56，面板开了 8 分钟）：

```
时间       分片       age  msg  req cold  in_ms  fwd alrm socks other intv
14:48:10  a0f991      62   48   44    0   1708  216   0     7     0    4
14:56:29  a0f991     561   53   48    0   5340  367   0     5     0    4
14:56:30  e8bbb6     562   24   24    0   1049  340   0     2     0    2
（14:56 面板关闭之后 → 0 条，实例立刻休眠）
```

三个可量化的判据，**全部满足就是正常快采**：

| 判据 | 正常快采 | 复发 |
|---|---|---|
| `msg / win_s` | ≈ `服务器数 × 1/5`（a0f991：4×12=48 ✓） | 与快采频率无关（慢采只有 ×1/120） |
| `ws_other` | **0** | 通常 > 0（CLOSING 挂着） |
| 面板关闭后 | `[stat]` 立刻消失 | `age_s` 继续爬到 ~900s（15 分钟上限）并持续整小时 |

补充特征：正常快采时 `close_*` 全为 0、`alrm=0`、`inflight=0`、`send_fail=0`，
`ws_states` 全是 `control:1*`；复发时最先异常的是 `ws_other`。

另一条独立的红线：**看小时 total**。正常快采下 14:00 那小时有 2,571 个请求，
但 duration 只有 117.7 GB-s（0.36 秒/条）；而根因未修时单实例整小时驻留就是 461 GB-s。
**请求涨了、duration 没跟着涨 → 快采；duration 按整小时量级走 → 复发。**

**当前用量已安全**：修复后约 1,750–1,900/天（13.5%–15%），最坏情况留 69% 余量，
不需要靠降采样换安全。若日后需要继续压，唯一不依赖平台行为的手段是降唤醒次数
（`REPORT_SLOW_INTERVAL_S` 120 → 300，总量 −60%，代价是无人观看时曲线粒度变粗）。

### 一个反例教训

本轮排查有两次结论被后续证据推翻，都值得记住：

1. **「78% 存活率 = 每 70–140 秒被 evict 一次」**——错的。`age_s` 实测到 721 秒连续存活，
   早已超过驱逐窗口，真实情况是**从未被驱逐**（每条消息都在推后驱逐计时器）。
   教训：用平均值反推机制时，先确认它对得上单实例的真实寿命。
2. **「`wallTime` 2.3 秒 = 在处理中卡了 2.3 秒」**——错的。`cpuTime` 只有 1–3ms，
   加 `[slow-msg]` 后打不出日志，说明 handler 内部 <1 秒，时间在 handler 之外（排队/唤醒）。
   教训：`wallTime` 不等于 handler 执行时间；判断「是否卡在代码里」要看 cpu 与分层埋点。
