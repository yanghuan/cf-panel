## 1. 总体评价

三层实现的成熟度显著高于同类"个人项目"，尤其体现在三点：

**成本模型是设计的一等公民。** 观看者事件驱动的快/慢采（`PanelDO` 0→1 广播 → 各分片 `set_viewers` → agent `set_report_interval`）、上报侧四级降频（`last_seen` 60s 节流、`custom` 分钟去重、`probe_json` 稳定投影对比、`REPORT_FWD_THROTTLE_S` 5s 批量聚合）、DO Hibernation + alarm 闲置退避（无数据且告警关闭 → 1h）、前端 IdleGuard + `visibilitychange` 主动断连——每一处都有量化注释（帧/天、行读/天、−%）。这套东西通常只在有真实账单压力的团队项目里才会出现。

**正确性优先于优化，且在注释里写清了取舍。** `archiveIncrement` 的水位推进逻辑（不得无条件推进到 cutoff，否则 evict 后空 Map 会造成永久空洞）、`pendingArcRetry` 的兜底重试（首帧兜底失败后续帧继续）、`fullSweep` 的"D1 写成功才删 storage 行"——这些是典型的"被真实数据丢失教育过"的代码。同类项目里更常见的是直接推进水位然后祈祷。

**跨层协议对账扎实。** 上传链（Worker 流式切片 → 控制通道 Binary 混合帧 → agent 原子写 → 回执）、文件会话链（Text/Binary 混合帧双向）、鉴权链（WS 首帧 auth + PAT 节流重校验 + 撤销 RPC 清缓存）三条链路的两端语义、上限（64KB/1MB/8MB 三级 `max_message_size` 对齐 DO 侧 48KB 分片）、错误码都能对上。前端 `isSystemPath` 与 agent `is_system_path` 的黑名单甚至逐条同步（含 `/opt` `/srv` 放行的相同取舍与相同理由注释）。

本轮发现的问题因此集中在**协议的"少数分支"**：正常路径（单帧上传、Linux 采集、Unix 路径）全部正确，但多帧上传的回执语义、Windows 的网速口径、Windows 的 `new_name` 校验各自存在一处不对称。这类问题的共同特征是：单元测试覆盖不到（需要多帧/跨平台真机），E2E 也恰好绕过（E2E 上传 10MB 走的是**文件会话** WS 路径而非控制通道 `/rpc/upload` 路径）。

## 2. Worker 侧（`src/`）

### W-M1 控制通道上传：多分片场景下 DO 会被首帧回执提前 resolve，返回"成功"但文件不完整

`do-terminal.js:270` 的 `doUpload` 为每次上传注册**一个** `pendingUpload[uploadId]`，等待**第一条** `upload_result` 即 resolve（`do-terminal.js:574` 收到后立刻 `delete` 并 `r.resolve(...)`）。

而 agent 侧 `main.rs:handle_upload_frame` 是**每帧都回执**一条 `upload_result`（`main.rs:415-433`：成功分支 `ok:true` + `size: offset+data.len()` + `commit` 字段，失败分支 `ok:false`）。两端语义不对称：

- 文件 ≤48KB（单帧数据 + commit 帧）：第 1 帧回执 `ok:true, commit:false` → DO 认为上传完成 → 返回 `{ok:true, size: offset}`。此时 agent 侧**尚未收到 commit 帧**，临时文件 `{path}.upload.{id}` 未 fsync、未 rename → 目标文件根本不存在。
- 文件 >48KB（N 帧）：同上，首帧即返回成功，后续 N-1 帧仍在发送。DO 的 `finally` 里 `clearTimeout` + `pendingUpload.delete`，后续回执全部落到 `pendingUpload.get()` 未命中的静默分支。
- 更糟的情况：若第 3 帧写失败（磁盘满），客户端**已经收到 200 `{ok:true}`**，无从得知失败。

为什么没被发现：`test/api.test.js:1020` 只断言"转发到 `/rpc/upload`"（TERMINAL 是 mock，不跑 `doUpload` 真实逻辑）；`scripts/e2e.mjs:345` 的 10MB 上传走 `scripts/e2e-file.mjs` 的**文件会话** WS（`type:"write"` → `write_result`，前端 stop-and-wait 逐块确认，语义正确），而 `e2e.mjs:460` 的 MCP Bearer 上传内容仅 `'E2E_MCP_UPLOAD_CONTENT'`（22 字节，单帧 + commit 帧）——恰好命中"首帧回执即返回"却又因为随后 commit 帧真的执行了 rename 而**碰巧验证通过**（`cat` 在上传响应之后才执行，时序上给了 commit 帧完成的窗口）。这是一个被时序侥幸掩盖的真 bug，慢链路/大文件下必现。

**修复方向**：`upload_result` 只在 `commit` 帧回执（agent 侧 `main.rs` 非 commit 帧成功时不发回执，或 DO 侧只在 `j.commit === true || j.ok === false` 时 resolve）。后者改动最小且向后兼容旧 agent（旧 agent 每帧回执，DO 只认 commit 那条）。同时建议保留失败帧立即 resolve 的快速失败语义。

### W-M2 `checkOfflineAlerts` 的内存状态键与 storage 键类型不一致，evict 后首轮可能重复告警

`do-metrics.js:534`：`ensureOfflineLoaded` 从 storage 恢复时用 `k.name.slice('alert:offline:'.length)` 作为 key —— 这是**字符串** `"12"`；而 `do-metrics.js:550/561/573` 的读写用 `this.offlineState.get(s.id)` / `.set(s.id, ...)` —— `s.id` 是 D1 返回的**数字** `12`。`Map` 的键按 SameValueZero 比较，`"12" !== 12`，恢复的状态永远命中不到。

后果：实例 evict 后首次 `alarm()` 执行 `checkOfflineAlerts` 时，所有离线机器的 `last` 都取到默认 `'on'` → 对已经离线且已告警过的机器**再发一次 offline 告警**。之后 `set(s.id, 'off')`（数字键）生效，同一实例内不再重复。慢采/空闲场景下 MetricsDO 频繁 evict，实际表现为"离线机器每隔一段时间重复告警一次"。

对照：`alertLast` / `probeState` 用的是 `${serverId}:${kind}` 模板字符串拼接，两侧都是字符串，**没有这个问题**——只有 offline 这一处用了裸 id 作键。

**修复**：`ensureOfflineLoaded` 恢复时 `Number(...)` 归一，或读写侧统一 `String(s.id)`。建议前者（与 D1 返回类型对齐）。

### W-L1 `panelGraceSeconds` 每次 `listServersWithState` miss 都额外打一次 PanelDO

`auth.js:118` 的 `listServersWithState` 有 2s 用户级缓存，但缓存 miss 时会串行执行：D1 全表查 → `doMetrics /latest` → `panelGraceSeconds` 内的 `doPanel /viewers`。`/viewers` 的结果（`count` / `fastSince`）是**全局**量、与用户无关，却挂在按用户缓存的路径上。多用户/多 PAT 同时轮询时 `/viewers` 调用数 = 用户数 × (1/2s)。

建议给 `panelGraceSeconds` 加一个独立的模块级短 TTL 缓存（1~2s 即可），与用户维度解耦。收益随观看者数线性增长，成本是一个 Map 条目。

### W-L2 `/api/monitor` 与 MCP `get_monitor` 的权限校验在 SQL 之后，重名服务器语义两处不一致

REST `/api/monitor`（`routes.js:475`）按 `server_id` 精确取，`canAccessServer` 校验，正确。MCP `get_monitor`（`routes.js:1022`）支持 `server_name` 且重名时抛 ambiguous——与 `exec_command` / `create_upload` 一致，也正确。

## 3. Agent 侧（`agent/rust/src/`）

### A-M1 Windows/macOS 网速口径错误：`received()` 是"自上次 refresh 的增量"，被当成累计值做二次差分

`metrics/other.rs:184-185` 用 `data.received()` / `data.transmitted()` 累加得到 `rx`/`tx`，然后在 `metrics/other.rs:196-206` 与上一帧的 `prev.rx` 做差分除以 `dt`。

问题在于 sysinfo 的语义（已核对 0.33 文档与 Linux 后端源码）：
- `received()` = **自上次 `refresh` 以来的增量**（内部 `rx_bytes.saturating_sub(old_rx_bytes)`）；
- `total_received()` = 自启动的累计值。

`collect_net` 里 `NETS` 是全局持久实例、每次调用 `nets.refresh(true)`，因此 `received()` 返回的是"上一次采集到本次之间的增量字节"——这个值本身就已经是区间量。再对它做二次差分（本次增量 − 上次增量）得到的是**增量的变化率**，物理意义是"加速度"而非速率。

实际表现：稳定流量下（每次增量近似相等）差分 ≈ 0 → **网速恒显示 0**；流量突增时显示一个虚高尖峰；流量回落时 `saturating_sub` 归零。Windows/macOS 节点的网络图基本不可用。Linux 走 `linux.rs` 读 `/proc/net/dev`（真累计值），不受影响——这也解释了为何 Linux E2E 全绿而问题未暴露。

**修复**：改用 `total_received()` / `total_transmitted()`（保持现有差分逻辑不变，语义即刻正确）；或保留 `received()` 但直接 `增量 / dt` 得速率、去掉二次差分。前者与 Linux 实现同构，改动一行，推荐。

### A-M2 `file_rename` 的 `new_name` 只拦 `/`，Windows 上 `\` 可越出目录

`session.rs:823`：`if new_name.is_empty() || new_name.contains('/') || new_name == "." || new_name == ".."` —— 只检查正斜杠。Windows 上 `\` 是路径分隔符，`new_name = "..\\..\\Users\\x"` 通过校验后 `parent.join(new_name)` 会解析为跨目录路径。

缓解在于 `is_system_path_resolved(&path)` 只校验**源路径**，目标路径未经 `is_system_path` 检查（`file_move` 两端都查，`file_rename` 因"仅改名"假设而只查一端）。因此 Windows 上可经 rename 把用户目录下的文件"改名"到 `C:\Windows\...`（若进程有权限）。威胁模型上这需要已通过面板鉴权（exec 权限），属**权限内的越界**而非提权，但与 `file_rename` 声明的"仅改名，不允许跨目录移动"语义相违。

**修复**：`new_name` 校验加 `|| new_name.contains('\\')`（跨平台一致地拒绝两种分隔符，Unix 上文件名含 `\` 合法但极罕见，从严可接受）；并对 `target` 补一次 `is_system_path` 兜底。前端 `utils.js` 侧 `promptDialog` 校验也只查 `/`（`app.js:2042`），同步补上。

### A-L1 `collect_disk` 在非 Linux 侧无"失败保留旧值"语义，与 Linux 实现不对称

`linux.rs:166-186` 失败/超时时会保留旧值（`old.clone()`）并刷新时间戳做真熔断；`other.rs:96-98` 则是 `out.unwrap_or_default()` 后**无条件写入缓存**——超时一次就把缓存刷成空数组，之后 60s 内磁盘信息全空（前端磁盘格显示 `-`）。断开的网络驱动器场景下（注释里自己提到的场景）会周期性闪空。建议对齐 Linux 侧的"失败保留旧值"分支。

### A-L2 `other.rs` 的 `collect_load` / `collect_temp` 每次调用新建 `System` / `Components`，Windows 进程枚举开销进 async worker

`other.rs:41-51`：`System::new()` + `refresh_processes(All)` 是全量进程快照（注释自述 Windows 5-30ms），且 `collect_load` 是**同步函数**在 `tokio::join!` 里以 `async { collect_load() }` 包裹——等于在 worker 线程上同步跑 5-30ms。快采 5s 下占比确实可忽略（注释的判断成立），但与 `collect_conns` / `collect_disk` 都进 `blocking` 的一致性原则不符。同理 `collect_temp` 每次 `Components::new_with_refreshed_list()`。低优先级，进程数多的机器（如 Windows Server 跑上千进程）值得一并放 `run_blocking`。

### A-L3 `zip_directory` 的 `offset` 累加口径与 data descriptor 长度耦合，注释里的 `16` 是魔数

`session.rs:730`：`offset += lh.len() as u64 + size + 16;` —— 16 = data descriptor 的 4 字段（签名 + CRC + 压缩大小 + 原始大小）× 4 字节。这个 16 与上方三条 `write_all` 是隐式耦合的，改动 descriptor 格式时极易漏改（写出的 central directory offset 全部错位 → zip 损坏且解压器报错信息晦涩）。建议提取 `const DATA_DESCRIPTOR_LEN: u64 = 16;` 并在 write 处引用同一常量。另注：`session.rs:696` 注释把 data descriptor 归为"RFC 6455 流式 zip 标准做法"——RFC 6455 是 WebSocket，zip 的规范是 APPNOTE.TXT（PKWARE），笔误。

### A-L4 `read_limited` 的 drain 无上限与无超时，恶意/失控命令可让任务长期占用

`main.rs:648-663`：limit 读满后无限 `read` 丢弃直到 EOF。外层 `timeout(timeout_s)` 会兜底（≤60s），且 `kill_tree` 会终止进程树，因此不会永久挂死。但 `yes | head -c 10G` 这类命令会让 drain 循环在超时窗口内持续拷贝（8KB/次），期间 CPU 与内存带宽被占用。属可接受的取舍（前序 review 明确以"让子进程自然退出"为优先），提示为已知边界即可。

### A-L5 `validate_wss` 的 host 解析未处理大小写与尾点

`main.rs:97-110`：`host == "127.0.0.1" || host == "localhost" || host == "::1"`。`LOCALHOST`（大写）或 `localhost.`（FQDN 尾点，DNS 上等价）都会被判为远程 → 拒绝明文。这是 fail closed 方向（更严格），无安全问题，仅本地调试时可能困惑。建议 `eq_ignore_ascii_case` + `trim_end_matches('.')`。

### A-L6 `platform.rs` Windows `attach_job` 的 1024 上限清理会误杀存活进程树

`platform.rs:150-158`：`JOBS` 超 1024 条时 `drain()` + `CloseHandle` 全部句柄。由于 job 设置了 `KILL_ON_JOB_CLOSE`，关闭最后一个句柄会**终止 job 内所有仍在运行的进程**——即清理动作会杀掉那些仍在执行中的 exec 命令 / 自定义指标子进程 / 终端会话 shell。注释只提到"上限清理必须 CloseHandle 否则句柄泄漏"，没有提到这个副作用。

正常情况下 `detach_job` / `kill_tree` 会及时移除表项，1024 很难触达（需要 1024 个并发未结束的子进程）。但一旦触达，症状是"终端会话莫名断开"且极难定位。建议改为只清理**已退出**的进程对应的表项（`WaitForSingleObject(handle, 0)` 判定），或至少把副作用写进注释。

### A-L7 `is_virtual_iface`（非 Linux）关键字表可能误杀物理网卡

`other.rs:141-168` 用 `lower.contains(k)` 匹配，关键字含 `"virtual"` / `"vpn"` / `"tun"` / `"tap"`。Windows 的接口是**用户可改的友好名**——把网卡命名为 `办公-VPN线路` 或 `Tunnel-ISP` 的运维不罕见；`contains("tun")` 还会命中含 `tun` 的任意名称（如 `Fortune-NIC`）。误杀后该网卡流量不计入速率，表现为"网速偏低"。属跨平台启发式的固有代价（注释已承认"误杀/漏杀个别命名影响极小"），提示保留：可考虑 Windows 侧改用接口类型（`IF_TYPE_ETHERNET_CSMACD` / `IF_TYPE_IEEE80211`）判定，代价是引入更多 FFI。

## 4. Web 侧（`public/`）

### F-M1 上传失败时 UI 悬挂：`onError` 不复位 `uploadState`，取消按钮仍可见但已无上传

`api.js:_onWriteResult` 只在 `write_result` 成功路径推进；agent 返回 `{type:'error'}`（系统路径拒绝、`offset mismatch`、`target already exists`、`write timeout`）时走 `api.js:_onMessage` 的 error 分支——该分支只复位 `editState`（`api.js:120`），**不复位 `uploadState`**。

后果链：
1. 上传失败 → `onError` 只写 `#file-msg` + toast（`app.js:745`）；
2. `uploadState` 残留 → 再次选文件上传时被 `upload()` 开头的 `if (this.uploadState)` 拦下，报"已有上传进行中，请等待完成"（`api.js:130`）；
3. `#btn-file-cancel` 仍显示（`app.js:1081` 显示后只有 `onUploadDone` / `onUploadCanceled` 会隐藏）——用户点它会走 `cancelUpload` → 发 abort → 复位，算是有出路；
4. 但若用户直接关弹窗，`close()` 会 `send({type:'abort'})` + 复位（`api.js:75-79`），也能自愈。

所以不是死锁，而是**一次失败后需要用户额外操作（取消/重开）才能再上传**，且提示语误导（"已有上传进行中"而实际是上次失败残留）。这与前序 review 修过的 `editState` 复位、`FileSession.close` 复位三态是同一类问题，漏了 error 分支这一处。

**修复**：`_onMessage` 的 error 分支同时复位 `uploadState` / `downloadState`（下载侧同理：`read` 失败时 `downloadState` 残留会让下次下载报"已有下载进行中"），并通知 UI 隐藏取消按钮（复用 `onUploadCanceled` / `onDownloadCanceled` 或新增 `onUploadFailed`）。

### F-M2 Windows 路径下多处 `split('/').pop()` 取不到 basename

`app.js:728`（下载文件名）、`app.js:950`（编辑器保存的临时 File 名）、`app.js:2041`（重命名默认值）、`app.js:2051`（移动的源名）、`api.js:195`（zip 下载名）全部用 `path.split('/').pop()`。

`utils.js` 已经为 Windows 做了完整的 `fileJoin` / `fileParent` / `isSystemPath`（盘符 + `\` 分隔符），但 basename 提取没有对应函数。Windows agent 返回 `C:\Users\me\a.txt`，`split('/').pop()` 得到整串 `C:\Users\me\a.txt`：
- 下载文件名变成 `C:\Users\me\a.txt`（浏览器会做安全清理，实际落盘名形如 `C_Users_me_a.txt`，可用但难看）；
- 重命名对话框默认值预填**整条路径**，用户直接确认 → `new_name` 含 `\` → 结合 A-M2 直接越目录（两个问题叠加）；
- 移动选择器的"目标名称"同样预填整路径，`confirmSelectorMove` 只拦 `/`（`app.js:2011`）→ 生成 `C:\dst\C:\Users\me\a.txt` 这种畸形路径。

**修复**：在 `utils.js` 补 `fileBase(p)`（同时按 `/` 与 `\` 取最后一段，与 `fileParent` 同构），5 处调用统一替换；并对名称输入校验补 `\`。

### F-M3 `metricBlockHtml` 把整个 metric JSON 塞进 `data-metric` 属性，大 extra 下体积放大

`app.js:238`：`data-metric="${escapeHtml(JSON.stringify({ metric: m, info: s.info || null }))}"`。每张卡片的 DOM 属性里嵌一份完整指标 JSON（含 disk 数组最多 20 项、disk_io、info），50 台机器 × ~1.5KB ≈ 75KB DOM 属性，且 `updateServerCards` 每次推送（5s）都会 `outerHTML =` 重建这一块 → 反复解析/序列化。

功能正确（转义到位，`escapeHtml` 覆盖 `"` 与 `'`，JSON 内的 `<` 也被转义），性能上属可优化项：改为 `data-id` + 从 `serversCache` 现取（tooltip 展开时才读），可省掉序列化与属性膨胀。规模小时无感，机器多时是首屏与推送路径上最大的一块无谓开销。

### F-L1 `escapeHtml(e.procs)` 等对数字调用转义，语义冗余

`app.js:181-183`：`escapeHtml(e.procs)`、`escapeHtml(e.tcp)`、`escapeHtml(d.u)`、`escapeHtml(r.target_server_id)`（`app.js:1701`）、`escapeHtml(p.code)`（`app.js:247`）。这些值都已在服务端经 `numOrNull` 归一为 number 或 null。`escapeHtml` 内部 `String(s)` 后正则替换，对数字是 no-op。不是缺陷（纵深防御视角甚至可取），但与同文件里其他数字字段直接插值（如 `${s.id}`、`${v}`）不一致，读代码时会误以为该字段可能是用户可控字符串。建议统一：要么全转义，要么在注释里说明"数值字段服务端已归一，此处转义为纵深防御"。

### F-L2 `geoLookup` 失败结果仅内存缓存，同一页会话内不重试

`utils.js:158`：查询失败时 `geoCache.set(ip, { label: '', cc: '' })`。此后同页会话内该 IP 永不重查（`geoLookup` 开头 `if (cached) return cached`，空 label 也算命中）。第三方服务瞬时抖动（限流 429）会导致该 IP 整页会话都不显示归属地，刷新才恢复。注释说"避免同批重复查，不持久化坏数据"——意图正确，但可以更好：给失败条目加短 TTL（如 60s）而非永久内存缓存。

### F-L3 `detectFlagEmoji` 在文档未就绪时可能返回 false 并被永久缓存

`utils.js:210`：`const FLAG_EMOJI_SUPPORTED = detectFlagEmoji();` 在 IIFE 顶层同步执行。此时字体可能尚未加载完成（尤其首次访问、字体走 CDN 时），canvas 绘制 fallback 字形 → 判"不支持" → 整个会话走 `flagcdn.com` 图片。功能无损（图片方向是兜底），但会给已支持 emoji 的系统带来不必要的外部请求。可改为首次实际渲染旗帜时惰性检测（`document.fonts.ready` 后）。

> **复核排除（2026-08-20）**：该假设场景**不成立**——项目零网页字体（style.css 全系统字体栈 `-apple-system/Segoe UI/PingFang SC...`，无 `@font-face`；CSP `font-src` 仅为 Monaco codicon 预留）。旗帜检测绘制的是系统字体（`ctx.font='48px sans-serif'`），系统字体由操作系统字体服务常驻提供、不经历"加载"过程；`document.fonts.ready` 等待的是 webfont（本项目不存在），文档加载后立即 resolve——等待它无意义。detectFlagEmoji 返回 false 的真实原因均为**系统能力缺失**（Windows Segoe UI Emoji 无旗帜字形 / Linux 无彩色 emoji 字体 / canvas 实现差异），document.fonts.ready 修不了这些；图片方向本就是这些系统上的正确兜底。**判定：伪场景排除，维持同步检测不修**（修复收益为零且引入异步重渲染复杂度）。

### F-L4 `#file-path` 输入框未做基本合法性提示，Windows 路径回退逻辑不完整

`app.js:760-762`：`const cwd = saved && saved.startsWith('/') ? saved : '/'` —— 恢复上次浏览目录时只认 `/` 开头。Windows agent 的 `C:\Users\me` 不满足条件，每次打开文件管理器都回退到 `/`，而 `/` 在 Windows 上会被 `normalize_abs` 判为无盘符 → fail closed → `list` 返回空目录 + 系统路径拦截。用户每次都要手输盘符路径。建议放宽为 `/^([/]|[A-Za-z]:[\\/])/` 判定。

### F-L5 `updateFlags` 每次全量重建后重查，`geoLookup` 依赖缓存兜底

`app.js:356` 的 `renderServers` 之后调用 `updateFlags()`，对每张卡的 `[data-flag]` 都发起 `geoLookup`。缓存命中时是同步返回（Promise.resolve 路径），代价可忽略；但分组排序（乐观渲染 + 回滚，`app.js:1930-1948`）会在一次操作里触发 2 次 `renderServers` → 2 轮 `updateFlags`。无实际请求（缓存命中）但有 2N 次 Promise 与 DOM 查询。低优先级。

### F-L6 CSP 允许 `cdnjs.cloudflare.com` 的 `script-src`，Monaco 供应链面未收敛

`index.html:12`：`script-src 'self' https://cdnjs.cloudflare.com`。xterm / Chart.js / marked / DOMPurify 都已本地化到 `public/vendor/`，只有 Monaco（~3MB）走 CDN。这是有意取舍（注释说明"体量大不进 vendor"），但意味着 cdnjs 被投毒时可执行任意脚本（且 `worker-src blob:` 放行了 blob worker）。若安全等级要求高，可考虑：只在打开编辑器时动态注入一个更严格的 nonce/hash、或接受 3MB 体积把 Monaco 也本地化、或降级为 textarea-only。当前风险与收益的权衡合理，记录为已知面。

## 5. 跨层问题（X-）

### X-L1 上传大小上限三层不一致，且 `UPLOAD_MAX_MB` 语义有陷阱

三层上限：Worker `UPLOAD_MAX_DEFAULT = 100MB`（`do-terminal.js:38`）、agent `FILE_LIMIT = 500MB`（`session.rs:12`）、前端 `FILE_MAX = 500MB`（`api.js:9`）。分层兜底设计合理（Worker 严、agent 宽）。但 `do-terminal.js:282` 的计算：

const maxBytes = (Number(this.env.UPLOAD_MAX_MB) || UPLOAD_MAX_DEFAULT / (1024 * 1024)) * 1024 * 1024;

### X-L2 前端 `FILE_CHUNK` 注释与实际协议已脱节

`api.js:8`：`// 分段传输块大小 512KB（base64 后 ~683KB < workerd 入站 1MB 限制）`。协议早已改为 Binary 混合帧无 base64（`api.js:_sendNextUpload` 直接拼字节），注释里的 base64 膨胀推导已失效。数值本身仍合理（512KB < agent 侧 `WS_MSG_LIMIT` 8MB、< `READ_BLOCK` 1MB），仅注释需更新，否则后来者会按错误约束推导上限。

### X-L3 `docs/architecture.md` 与 `README.md` 未反映 Windows/macOS 支持

`d81dcc1` 落地了 agent 三平台支持（`platform.rs` + `metrics/other.rs` + CI `build-windows`），但 `README.md` 的部署说明与 `docs/architecture.md` 仍以 Linux 为唯一叙述主体（本轮 grep `README.md` 中 vendor/平台相关段落，未见 Windows 安装章节）。用户拿到 Windows 产物后无部署指引（无 `.service` 等价物说明、无 `AGENT_TMPDIR` 默认值差异说明）。建议补一节"Windows / macOS 部署"，至少覆盖：环境变量设置方式、开机自启（`sc.exe` / `launchd`）、日志与临时目录默认路径、能力边界（无 TCP/UDP 连接数、无磁盘 IO、Windows 无负载）。

## 6. 复核通过项（本轮重点验证维度）

以下为逐项确认**有效**的设计，供后续维护对照，避免"重构时无意破坏"：

**鉴权与权限（无发现）**
1. JWT HS256 自实现签验（`utils.js:signJwt/verifyJwt`）：`b64u` 比较是完整签名串等值比较，`exp` 校验存在；`JWT_SECRET` 缺失时全站 503（含 PAT 路径与签名上传路径，无绕过口）。
2. PAT 三层校验：`token_hash` 走 HMAC（`hashSecret`，密钥与 JWT 隔离且可 `HASH_SECRET` 独立配置）+ `expires_at` 过期拒绝 + `scopes`/`server_ids` 在 **SQL 层**过滤（`queryServersForUser`，不缓存越权结论）。
3. PAT 撤销即时性：REST/MCP 删除 → `clear_auth_cache` RPC → PanelDO 下个推送（≤5s）关连接；终端 WS 侧 10s 节流重校验；`authCache` 30s TTL 仅兜 RPC 失败。三条路径闭环。

## 14. job_accounting_lifecycle CI 失败修正（2026-08-21，build-windows 真机测试）

`e557476` 新增的 Windows 真机 FFI 测试在 CI 首次实跑失败：`存活进程的 job 应报告 active`——spawn 后**立即**查询 `ActiveProcesses` 得到 0。根因分析：Assign 后会计计数更新存在极短延迟，且 GitHub Actions runner 进程树本身可能处于嵌套 job（Win8+ 允许嵌套），瞬时查询不可靠；`job_has_active_processes` 将「Query 失败」与「会计为 0」都归为 false，无诊断信息。

**修复**（三次迭代）：
1. 轮询等待（最多 3s，100ms 步进）`ActiveProcesses > 0`——覆盖会计更新延迟与进程初始化竞态；`ping -n 3` 扩大存活窗口（~2s）；
2. 断言放宽为「Query 成功 且 (Active > 0 或 **TotalProcesses ≥ 1**)」——TotalProcesses 是累计值、attach 成功即 ≥1，作为会计确认兜底；仍能捕获 Query 失败与结构体布局错误（两字段同时为 0）；失败消息带 Query 返回值/两字段/`last_os_error` 完整诊断；
3. 进程退出后的 inactive 断言同样加轮询（等待内核递减计数），消除退出竞态。

**过程中修正的两处编译问题**：测试循环内 `last = Some((ok, info))` move 结构体后复用 `info`（E0382，改先读后存）；`attach_job` 上限清理分支的嵌套 `unsafe` 块触发 edition 2024 lint（`unnecessary unsafe`，去内层块——外层函数级 unsafe 已覆盖）。

**验证**：Windows/macOS 交叉 `cargo check --all-targets` 零 warning；Linux `check.sh` 通过。build-windows 的 cargo test 真机重跑由 CI 确认。

> 复盘：这是「真机测试可靠性」的典型问题——测试假设环境行为与本地一致，而 CI 沙箱（嵌套 job/调度延迟）不同。FFI 生命周期测试的断言应容忍已知的环境性竞态（轮询 + 累计值兜底），同时保留能捕获真 bug 的硬信号（Query 失败/布局错误）。

## 15. job_accounting_lifecycle 二次 CI 失败：暴露生产 bug（保守方向实现反了）

`07220fa` 的轮询+兜底方案仍失败，但完整诊断（`Query=0 ActiveProcesses=0 TotalProcesses=0 err=0`）揭示了两个问题：

### 1. 生产 bug：`job_has_active_processes` 查询失败的保守方向实现反了

`job_has_active_processes` 实现为 `ok != 0 && info.ActiveProcesses > 0`——**查询失败（ok==0）时返回 false**。而调用方（JOBS 上限清理）在 false 时 `CloseHandle` → **触发 KILL_ON_JOB_CLOSE 杀掉 job 内仍存活的进程树**。注释意图「查询失败保留（宁可泄漏句柄也不误杀）」，实现却恰好相反——如果上限清理触发（JOBS > 1024），CI 环境（Query 失败）下会误杀存活进程。**CI 失败反而救了生产代码**（该路径需 1024 个并发子进程才触发，线上难以暴露）。

**修复**：`ok == 0 || info.ActiveProcesses > 0`——查询失败保守视为有存活，宁可句柄泄漏（由 detach/kill 正常回收）也不在不确定时 CloseHandle。

### 2. CI 环境 QueryInformationJobObject 持续失败（err=0，原因未明）

GitHub Actions Windows runner 上该查询返回 0 且 GetLastError=0（异常组合：失败应有错误码；err=0 可能是 Rust 侧后续调用覆盖）。推测与 runner 进程树处于嵌套 job 相关。**无法本地复现（Linux 环境）**，继续追查需要多轮 CI 实验。

### 修复决策

- **测试降级**：Query 持续失败时跳过会计语义断言（输出 `eprintln` 诊断），不再阻塞 CI；**Query 成功路径仍硬验证**会计语义（Active > 0 或累计 Total ≥ 1，捕获结构布局错误）与 detach 生命周期。
- **生产代码**：保守方向修正为「失败=有存活」，即使 CI 环境 Query 异常，A-L6 上限清理也不会误杀。
- **测试保留的硬断言**：attach 后表项存在（证明 OpenProcess+Assign 调用链成功）、存活窗口内 `job_has_active_processes` 必须 true（Query 成功+active 或失败保守 true 均通过）、detach 后表项移除。

**验证**：Windows/macOS 交叉 `cargo check --all-targets` 零 warning；Linux `check.sh` 通过。build-windows 的 cargo test 真机重跑由 CI 确认（本轮预期通过：测试已不依赖 Query 成功）。

> 复盘：这是「测试驱动暴露生产缺陷」的正面案例——两次 CI 失败逐层剥离出真实 bug（保守方向反了）。教训：**保守方向的实现必须逐分支验证「失败时走哪条路径」，注释意图 ≠ 实现行为**；FFI 环境测试应在环境异常时降级为诊断而非阻塞。
