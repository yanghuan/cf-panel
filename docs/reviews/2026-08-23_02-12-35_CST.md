## 1. 发现详情

### F-H1 文件列表渲染：`e.type` / `e.size` 未转义进 HTML 属性（XSS，已修复）

`public/app.js:799-803`：同一行内 `data-path` 与 `e.name` 都经 `escapeHtml`，唯独 `data-type="${e.type}"`、`data-size="${e.size}"` 原样插值。

威胁模型成立依据：DO 对 agent→浏览器帧是**纯字节透传**（`do-terminal.js` 注释明示）；而 `report.js` 对 agent 上报按不可信输入做了白名单收口——同一输入源在文件列表路径漏了。被入侵/恶意 agent 返回 `{"type":"\"><img src=x onerror=...>"}` 的条目，管理员开一次「文件管理」即在面板 origin 执行任意 JS → 窃取 localStorage JWT → 横向接管全部服务器（终端 exec / PAT 创建）。附带影响：非数值 `size` 使 `fmtBytes` 内 `.toFixed` 抛 TypeError，整个列表渲染中断（行内 `editable` 判定因 NaN 比较恰为 false，编辑按钮不渲染，但下载/删除按钮恒渲染）。

**修复方向**：类型白名单化 + 数值强转：
```js
const type = e.type === 'dir' ? 'dir' : 'file';
const size = Number(e.size) || 0;
```
长期看 DO 侧应对 entries 做与 report 同级收口（type/name 长度上限、size 数值化）。

**修复实现**：新增 `normalizeFileEntry`，在任何条目进入格式化和 HTML 拼接前将 `type` 白名单化为 `dir/file`、将 `size/mtime` 归一为有限非负数，并限制名称长度；所有名称/路径仍保留 HTML 属性转义。恶意 `type/size` 回归测试已覆盖。

### A-H1 控制通道上传首帧预检裸跑 async 读循环（已修复）

`main.rs:403`：

```rust
if offset == 0 && !overwrite && std::path::Path::new(&path).exists() {
```

紧随其后的 `write_bytes`（417 行）包进 `file_blocking(30)`，且 411-413 行注释明确描述过这类风险：「挂死挂载点上……挂死会连坐控制读循环（超时作用域外 await）」。预检这行恰好漏在封装外。对照 `session.rs:1080`：文件会话的同款检查在 `file_blocking(30)` 闭包**内部**完成。

触发：服务端下发 upload 帧、path 指向挂死 NFS/SMB → `stat()` 内核态无限阻塞 → 控制读循环永久卡死：心跳 pong 停发、半开检测失效、全部指令失效，agent「假活」只能重启。`CONTROL_READ_TIMEOUT_S` 只包住 `read.next()`，dispatch 内的 await 在超时作用域之外。

**修复方向**：把预检移入 `file_blocking` 闭包内（与 session.rs 同构，一行级改动）。

**修复实现**：`exists()` 已与 `write_bytes` 一并移入 `file_blocking(30)`；超时会将 upload 标记失败，后续分片不再继续写入。

### W-M1 fullSweep 批次失败仍删行 + 推水位 → 历史永久空洞（已修复）

`do-metrics.js:704-724`：704 行注释声明不变量「D1 写入成功后才删除 storage 行」，但实现中批次失败仅 console.error（709 行），随后 713 行**无条件**删除 `keysToDelete`、721-724 行照常推进 `arcMax` 水位。失败批次的行既没进 D1 又从 storage 删除，且水位推进后 `archiveIncrement` 与后续 fullSweep 都只处理 `ts > arcTs` → 该区间历史永久空洞。fullSweep 本就是兜底路径（正常增量归档失败有 `pendingArcRetry` 保水位重试），此处行为与其直接不一致。

**修复方向**：记录每批覆盖的行（stmts 本就有序），批次失败时把对应 key 从 `keysToDelete` 剔除且不推进相应 serverId 水位——保住「prune 不被归档失败连累」目标的同时守住不变量。

**修复实现**：按服务器隔离归档批次；任一批失败时保留该服务器本轮全部源行和旧水位，成功服务器仍可独立完成。`fullSweep()` 返回完成状态，D1 写入、源行删除和水位持久化全部成功后才推进家政时间戳；成功批次通过 `INSERT OR IGNORE` 安全重放。

### A-M1 自定义指标 stdout 无上限物化（已修复）

`metrics/mod.rs:216-222`：`read_to_end(r, &mut buf)` 在 5s timeout 内读满管道吞吐，buf 只用于取第一行（228 行）。exec 路径为此专门写了 `read_limited`（main.rs:772 注释：「刷屏命令……无界物化导致峰值内存数百 MB」），此处漏配同款防护。`tail -f`/`journalctl -f`/失控脚本误配即触发，小内存 VPS 被 OOM killer 连 agent 一起杀。

**修复方向**：复用 `take(cap)`（首行解析只需几 KB）。

**修复实现**：复用 `read_limited`，仅保留 stdout 前 4KB、继续 drain 剩余管道；读取与 `child.wait()` 共同受 5 秒总超时保护，超时仍终止完整进程树。

### A-M2 单挂载点失败拖垮整份磁盘列表并污染缓存（已修复）

`metrics/linux.rs:226`：`let md = std::fs::metadata(mount).map_err(|_| ())?;` —— `?` 使整个 `disk_usage_static` 返回 Err；233 行同类 statvfs 失败却是 `continue`。失败进入 collect_disk 的 `_ =>` 分支（175-185 行）：首次失败且无旧值 → 写空缓存 60s；过期重试仍失败（坏挂载点还在）→ `old` 即空 → **永久空**。ESTALE 的过期 NFS、0700 目录无权穿越、autofs 触发失败均可触发，面板磁盘区从此黑屏。与刚修复的 other.rs「collect_disk 失败保留旧值」（A-L1 前序）同类不同枝。

**修复方向**：`map_err(|_| ())?` 改 `continue`；空结果不覆盖非空旧缓存。

**修复实现**：挂载点 `metadata` 失败改为逐项跳过，且只有成功采集后才提交设备去重键；全空刷新保留最近一次非空缓存并刷新熔断时间。

### A-M3 file_zip 预检裸跑 async（已修复）

`session.rs:766`（`std::fs::metadata`）、`:789`（`walk_dir_size` 全树同步递归）在 async fn 里直跑，无超时无熔断；真正的打包（804 行）反而包了 `file_blocking(120)`。含挂死子挂载点的目录点「下载 zip」→ read_dir/stat 永久阻塞占死一个 tokio worker（不可取消的 future），反复重试耗尽 worker 后整个 agent 冻结。与全局「FS 操作必须走 blocking 封装」设计矛盾（同 A-L2 前序修过的 collect_load 一类）。

**修复方向**：metadata + walk_dir_size 移入 `file_blocking(60)` 闭包。

**修复实现**：metadata、带上限的全树大小预检和 STORED ZIP 写出均收敛到同一个 `file_blocking(120)`；预检超过 500MB 后提前停止遍历，失败统一清理半成品。

### F-M1 FileSession.open 竞态（已修复）

`public/api.js:42-63`：`close()` 后 `await api('/api/file/open')`，返回后无条件 `new WebSocket` 并覆盖 `this.ws`，无代际检查。场景 A：fetch 返回前用户关弹窗 → 孤儿已认证 WS 泄漏到服务端 TTL。场景 B（更严重）：快速切换服务器或 reconnect 与手动 open 重叠、响应乱序 → 旧续延把 `this.ws` 覆盖为**旧服务器** socket，此后 rename/delete/upload 全部打到错误机器。TermSession 有 `if (this.closed) return` 守卫（api.js:323），FileSession 缺失。

**修复方向**：代际计数器 `const gen = ++this._gen;`，await 后 `if (gen !== this._gen) return;`。

**修复实现**：`FileSession` 新增单调 `_generation`；`open()` 的 API 响应及 WS open/message/close 事件均校验代际和当前 socket，`close()` 立即使所有在途操作失效。已覆盖关闭后迟到响应和并发乱序响应。
