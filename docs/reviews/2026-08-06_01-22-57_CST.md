## 2. 分发体积专项

已实施的优化（`Cargo.toml:28-32`）：`opt-level="z"` + `codegen-units=1` + `lto=true` + `strip=true`，且作者实测论证了不采用 `mimalloc`（RSS 反升）与 `panic="abort"`（保留 task panic 隔离）——**决策有据，保持**。

依赖构成：`tokio` + `rustls`（webpki-roots 内嵌根证书）+ `tokio-tungstenite` + `portable-pty` 为主要体积来源，均按需引入，无冗余大件。

可选进一步压缩（非必须）：

1. **UPX 压缩**：约 1.98MB → ~0.7-0.8MB。代价：启动解压 ~50ms、部分杀软误报。适合作为发布页的附加产物而非默认。
2. `tokio` 改 `rt-current-thread`：省约几十 KB 与数个线程，但失去 worker 并行（采集/会话 IO 并行度下降），**不建议**。
3. 其余空间（裁 rustls 根证书、去 serde_json 改手写）收益小、维护成本高，不建议。

## 3. 问题清单（按严重级别）

### High

**H1. 阻塞线程池泄漏耗尽：挂死挂载点上的 `df` / 文件操作**
`metrics.rs:29-39`（`run_blocking`）、`metrics.rs:145`（每周期 `df -Pk`）、`session.rs:322-332`（`blocking_with_timeout`，file_list/read/write/abort 同模式）。
`tokio::time::timeout` 超时后 drop `JoinHandle` **不会取消** `spawn_blocking` 任务（tokio 语义：阻塞任务不可中断）。`df` 撞挂死的 NFS/CIFS hard mount 进入 D 态，永久占住一个 blocking 线程（默认上限 512）；挂死的 `df` 进程同时成孤儿。
- **耗尽时间**：快采 5s 周期 ≈ 43 分钟；慢采 120s ≈ 17 小时。文件操作（`session.rs:364/421/479/566`）可被前端重试放大，分钟级耗尽。
- **后果**：池耗尽后磁盘采集、文件 list/read/write 全部静默超时失败，控制通道仍活——无任何告警的静默降级。
- **修复**：① `df -Pkl` 仅本地文件系统（或解析 `/proc/mounts` 跳过 `nfs/cifs/fuse.*` 后对本地挂载 `statvfs`）；② 连续超时路径熔断跳过；③ df 结果缓存 60s；④ `Semaphore` 限制并发阻塞数。

**H2. http 探活不支持域名（真 bug，功能回退）**
`metrics.rs:271`：`format!("{host}:{port}").parse::<SocketAddr>()` 只接受 IP 字面量——`http://example.com/` 解析失败返回 `None` → **域名探活永远 DOWN**，且持续触发服务端探活告警（`src/do-metrics.js:451`）。对比 `tcp_probe`（`metrics.rs:298-312`）有 `lookup_host` DNS 兜底，http 路径缺失。shell 版用 curl 天然支持域名，属回退。
- **修复**：`parse` 失败时回退 `tokio::net::lookup_host((host, port)).await`（与 tcp_probe 对齐，约 5 行）。

**H3. 控制通道无读超时，半开连接假在线**
`main.rs:200`：`read.next().await` 无超时。NAT/防火墙静默断链时依赖 TCP keepalive（Linux 默认 7200s）才发现，期间**面板显示在线但已失联**（断链后无上报，MetricsDO 宽限后判离线——但 agent 自身不知，恢复前不重连）。shell 版有 `read -t 180` 自愈。服务端 30s 心跳（`src/do-terminal.js:443`）保证健康连接必有下行流量。
- **修复**：读循环包 `timeout(180s)`，超时即断开重连（健康连接 30s 必有 ping，180s 无消息必异常）。

**H4. 连接秒断重置退避 → 固定 ~3s 重连风暴**
`main.rs:139-143`：`control_conn` 返回 `Ok`（连接成功但服务端立即关闭，如反代错误配置/服务端 bug）→ `backoff = RETRY_INITIAL` → 每 ~3s 重连，**每天 28,800 次**（对 Worker/D1 是放大，与 401 长退避的设计目标相悖）。
- **修复**：记录连接建立时长，存活 <10s 的"成功连接"也走指数退避（仅存活 ≥10s 才重置 backoff）。

### Medium

**M1. `/proc/net/tcp|udp` 全量物化 + 同步读**
`metrics.rs:24-26, 133-141`：`read_to_string` 一次性物化后仅 `lines().count()`。50 万 TCP 连接 ≈ **75MB 瞬时 String** + 阻塞 worker 线程数十~数百 ms（快采 5s 周期下反复大分配）。
- **修复**：`BufReader::lines().count()` 流式计数（内存 O(1)），或移入 `spawn_blocking`。

**M2. unwrap 崩溃路径**
- `session.rs:126, 230`：`cfg.key.parse().unwrap()`——key 含非法 header 字符时 panic（控制通道 `main.rs:180` 用了 `?`，终端/文件通道不一致）。配置错误应友好退出而非 panic。
- `session.rs:263`：`created.lock().unwrap()`——Mutex poison 时 panic（实际几乎不触发）。
- `main.rs:105, 117`：`CONFIG.get().unwrap()`——启动顺序保证安全，实际不可达。

**M3. `set_report_interval` 未校验下限**
`main.rs:224-228`：接受 `interval=0` → `report_loop` 紧循环（采集+发送无间歇），agent CPU 打满、服务端被打爆。异常/恶意服务端消息即可触发。
- **修复**：`iv.clamp(1, 3600)`（一行）。

**M4. 采集全链串行 await，周期被拉长**
`metrics.rs:412-421`：cpu 200ms + df（最坏 5s）+ uname（5s）+ hostname（5s）+ probes（5s/个）+ custom（5s/个）**串行**。多 probe/custom 时单轮采集可达数十秒，快采 5s 帧率被稀释、上报延迟增大。
- **修复**：无依赖的采集项 `tokio::join!` 并行（注意 NET 差分互斥与 blocking 池占用）；info/disk 可降频缓存（见 M7）。

**M5. SIGTERM 清理与会话任务清理双调用 `cleanup` → PID 复用风险**
`main.rs:416-419`（遍历 sessions 调 cleanup）与 `session.rs:103`（run_terminal 任务退出时调 cleanup）竞态：第一次 `child.kill()` 后 PID 已释放，第二次仍执行 `kill(-pid, SIGHUP)`（`session.rs:83`），若 PID 被复用为无关进程组 leader 则**误杀无关进程**。
- **修复**：`TermSession` 加 `AtomicBool cleaned`，cleanup 入口 compare_exchange 幂等（~5 行）。

**M6. 日志同步写阻塞 worker**
`main.rs:114-123`：`log()` 同步写文件 + stdout。**stdout 接管道且对端不消费**（64KB 管道缓冲写满）时 `write_all` 永久阻塞 worker 线程（容器/pipe 场景；systemd 直跑风险低）。另每条日志一次 `metadata()` syscall。
- **修复**：mpsc + 专用 OS 写线程，async 侧 `try_send` 丢弃降级；或至少文档声明 stdout 阻塞前提。

**M7. 每帧 fork 外部进程（快采下放大）**
`metrics.rs:145`（df）、`229`（uname）、`234`（hostname）、`389`（custom sh）：快采 5s → 每天 ~3×17,280 次 fork+exec，而 info（OS/内核/IP）基本不变。
- **修复**：info 缓存 10min TTL（服务端本就变化才写 D1）；disk 缓存 60s（同时缓解 H1 触发频率）。

**M8. 僵尸会话的 ready 回执（窄窗口）**
`main.rs:243-251`：旧会话数据面已断（`session.rs:127-133` 返回）但尚未移出 map 的窗口内，DO 确认重发到达 → 回 `terminal_ready` 但不再 spawn → 死终端（DO 停止重发）。
- **修复**：`TermSession` 加 `alive: AtomicBool`，ready 分支仅 alive 时直接回执，否则先移除旧项再 spawn。

**M9. bash 自然退出后终端挂死**
`session.rs:197`：reader 线程 EOF → send_task 结束，但 WS 读循环仍挂起 → 死终端等会话 TTL（10min 双断/4h 绝对）才回收。
- **修复**：`select!` 同时监听 send_task 完成句柄，pty 消亡即主动关闭 WS 退出。

## 4. 逻辑正确性：验证为正确的关键点

以下逐项复核**确认无误**（防止后续误改）：

1. **open_terminal 幂等无 TOCTOU**：dispatch 在控制通道读循环串行 await（`main.rs:200-205`），`contains_key→spawn→insert` 无并发窗口；`Arc::ptr_eq` 防旧任务误删新会话（`session.rs:105-112`）。
2. **合帧逻辑**：超限整批发送（<32KB+8KB 远低于 workerd 上限）、窗口到期/通道关闭先 flush 再退出、bash 退出时 channel 排空后尾部 flush——无丢数据、顺序保持。
3. **file_write**：严格 offset 校验（防丢块/乱序）、upload_id 隔离、commit fsync+rename 原子替换、失败仅留临时残留不破坏目标——与 Worker stop-and-wait 协议闭环。
4. **file_read 边界**：offset>size 无下溢、limit=0 封顶 READ_BLOCK、got=0 前端中止契约闭环。
5. **wildcard_match**：贪婪+单星回溯算法正确、有界不死循环。
6. **网络差分**：列偏移与 `/proc/net/dev` 格式一致、计数器回绕/接口增删有防护、与 shell awk 口径对齐。
7. **CPU 双采样**：算法与 shell 版逐字段一致、clamp 0-100。
8. **上报契约**：全部字段名/类型/嵌套与服务端 `handleReport`、前端消费一致（含 `temp` 可 null、`disk:{m,u}`、`probes[].ok` bool 兼容）。
9. **SIGWINCH 链路**：master resize → TIOCSWINSZ → 内核自动向前台进程组发 SIGWINCH，正确。
10. **退避与 401**：指数退避 + 抖动 + 401 长退避 + tungstenite Http 错误识别，测试覆盖。

## 7. 测试缺口

1. http 探活仅 IP 字面量——无域名用例（H2 漏网原因）。
2. 无 blocking 池泄漏回归测试（H1）。
3. 无重连退避行为测试（H4 秒断场景）。
4. 无 cleanup 幂等/双调用测试（M5）。
5. 合帧/文件协议有单测，但无与真实服务端的端到端压力用例（E2E 覆盖基本链路）。

## 8. 总评

实现质量整体较高：体积（1.84MB gnu / 1.98MB 静态）与内存（4MB 基线）对低内存设备友好，安全与正确性细节（幂等、原子写、背压、退避抖动）到位。**主要风险集中在阻塞模型的边界**（H1 线程池泄漏、H3 半开检测、M1 大文件物化）与**少数健壮性缺口**（H2 域名探活、H4 秒断风暴、M3 下限校验）。P0 四项均为极小改动，建议优先合入。
