# cf-panel 全项目代码 Review

- **审查时间**：2026-08-04 18:24:41 CST
- **审查范围**：Worker 后端（`src/index.js`）、D1 Schema、Durable Objects、前端（`public/`）、Rust Agent（`agent/rust/`）、systemd 服务、CI/CD、测试、部署配置与项目文档
- **审查方式**：全仓库静态审查、跨模块协议核对、现有测试执行、依赖漏洞审计
- **风险口径**：Critical = 可直接导致系统接管或核心安全边界失效；High = 高概率导致数据丢失、权限扩大、资源耗尽或生产核心能力失效；Medium = 需要特定条件、影响受限或主要影响可靠性；Low = 防御纵深、可维护性、体验问题

## 1. 结论摘要

项目整体结构清晰，Worker、Durable Object、D1、静态前端和 Rust Agent 已形成完整闭环；现有 Node 测试覆盖面明显好于同规模项目，鉴权、PAT、MCP、DO 会话、告警和归档均有基础测试。

但当前仍不建议在公网无额外防护的情况下直接承载高权限生产主机，主要原因是：

1. `JWT_SECRET` 缺失时会回退公开固定值 `dev-secret`，属于 fail-open，可导致完整管理员身份伪造。
2. MetricsDO alarm 被持续上报不断后推，归档、数据清理和离线告警在正常运行状态下可能永不执行。
3. 归档流程先启动删除 DO Storage、后写 D1；D1 失败时可能永久丢失唯一副本。
4. 终端/文件会话无配额，终端重试在 Agent 侧非幂等，可批量创建 PTY/bash 并耗尽主机资源。
5. 文件上传无背压且直接覆盖最终文件，断线、解码失败或超时会留下截断/半写文件。
6. systemd 默认以 root 启动带远程 shell 和任意文件读写能力的 Agent，凭据泄露或控制面失陷时影响为整机接管。

## 2. 架构与数据流概览

### 2.1 Worker 后端

- `src/index.js` 同时实现 REST API、JWT/PAT 鉴权、MCP、监控查询以及三个 Durable Object。
- `TerminalDO` 按 4 个固定分片中转 Agent 控制通道、终端流和文件流。
- `PanelDO` 负责面板服务器列表推送。
- `MetricsDO` 单实例保存分钟级热数据、执行告警、归档与保留期清理。
- D1 保存服务器、PAT、审计、历史监控、自定义指标和面板设置。

### 2.2 前端

- 无构建静态 SPA，使用原生 JavaScript、Chart.js 和 xterm.js。
- JWT/PAT 保存在 `localStorage`，REST 通过 Bearer 头鉴权，WebSocket 在首帧发送 token。
- 终端直接通过 xterm.js 与 TerminalDO 透传；文件管理使用 JSON + base64 分块协议。

### 2.3 Rust Agent

- 单进程 Tokio Agent，维持控制 WebSocket，按指令创建终端或文件数据通道。
- 监控读取 `/proc`、调用 `df`/`uname`/`hostname`，支持 TCP/HTTP 探活和自定义命令指标。
- systemd 服务默认拥有完整主机权限，并提供 PTY shell 与文件读写。

## 3. Critical

### C-01 缺少 `JWT_SECRET` 时使用公开固定密钥，生产环境可被直接接管

- **位置**：`src/index.js:83-85`、`src/index.js:108-125`、`src/index.js:184-186`；`wrangler.toml:41-44`
- **现象**：`secret(env)` 在未配置 `JWT_SECRET` 时返回固定字符串 `dev-secret`。JWT 签名和未单独配置 `HASH_SECRET` 时的 Agent/PAT 哈希都依赖该值。
- **攻击场景**：部署者配置了 `PANEL_PASSWORD`，但遗漏 `JWT_SECRET`；攻击者无需知道登录密码即可离线生成 `role:1` 管理员 JWT，调用终端和文件接口。README 虽提示必配，但运行时没有拒绝启动或拒绝登录。
- **影响**：面板管理员权限、所有已接入主机的远程 shell/文件访问能力完全失守。
- **修复建议**：
  1. 生产请求路径发现 `JWT_SECRET` 为空时直接返回明确的 503 配置错误，禁止登录和受保护接口。
  2. 删除生产代码中的固定回退；本地测试通过显式 `.dev.vars` 提供开发密钥。
  3. 强制最小长度并支持密钥版本/轮换；`HASH_SECRET` 与 JWT 密钥必须独立。
  4. 将当前“回退固定密钥”的单元测试改为“缺密钥拒绝服务”。

## 4. High

### H-01 MetricsDO alarm 会被持续上报无限后推

- **位置**：`src/index.js:1430-1442`、`src/index.js:1526-1531`、`src/index.js:1648-1700`
- **现象**：每次 `/report` 都把唯一 alarm 重设为 `Date.now() + 10 分钟`。Agent 正常每 3 秒或 120 秒上报，均小于 10 分钟。
- **影响**：只要任意 Agent 持续在线，归档、热区清理、30 天指标清理、90 天审计清理、离线/恢复告警都可能永不执行。所有服务器共用一个 `MetricsDO("main")`，问题具有全局性。
- **修复建议**：读取 `getAlarm()`，仅在没有 alarm 或新时间更早时设置；alarm 结束后固定重排，并在 `finally` 中保证异常时仍会注册下一次 alarm。补充“高频上报不推迟已有 alarm”的测试。

### H-02 归档在 D1 成功前启动删除 DO Storage，失败时永久丢数据

- **位置**：`src/index.js:1655-1680`
- **现象**：循环中执行 `this.state.storage.delete()` 并保存已启动的 Promise，之后才执行 `env.DB.batch(stmts)`。
- **影响**：D1 batch 因配额、批次过大或临时故障失败时，Storage 删除仍可能完成，数据在两端都不存在。
- **修复建议**：先收集语句和 key，按有界批次写 D1；每批确认成功后再删除对应 Storage key。保留 `INSERT OR IGNORE` 以支持幂等重试。

### H-03 热区/D1 查询硬切换形成确定的数据空洞

- **位置**：`src/index.js:17-20`、`src/index.js:224-241`、`src/index.js:1654-1680`；`README.md:322-325`
- **现象**：≤12h 只查 DO，>12h 只查 D1；但 alarm 把超过 60 分钟的数据从 DO 删除。
- **影响**：
  - 12h 查询正常仅剩约 1h；
  - 3d/7d/30d 查询缺少尚未归档的最近约 1h；
  - `ARCHIVE_TO_D1=0` 时文档声称保留 12h，代码实际上约 1h 后删除。
- **修复建议**：所有范围按时间边界合并 D1 和热区，以 `(server_id, ts)` 去重后再降采样；或至少将热区删除阈值恢复为 720 分钟，并修正文档与测试。

### H-04 终端/文件会话无配额，可耗尽 Agent 和 DO 资源

- **位置**：`src/index.js:625-662`、`src/index.js:979-1011`、`src/index.js:1122-1147`；`agent/rust/src/main.rs:144-185,262`
- **现象**：API、TerminalDO 和 Agent 都没有每用户、每服务器或全局并发上限。只要 Agent 数据流一端保持连接，会话不会按 10 分钟 TTL 回收。
- **攻击/失败场景**：持有合法 exec 权限者循环调用 `/api/terminal`，不连接浏览器；Agent 仍创建 bash/PTY 并连接数据 WS，会话可长期存活。
- **影响**：耗尽进程、PTY、FD、线程、WebSocket、DO 内存/Storage。
- **修复建议**：API/DO 与 Agent 双层配额；Agent 使用 `Semaphore`；创建后 15–30 秒无浏览器鉴权则回收；增加绝对最长会话时长和 429/503 测试。

### H-05 `open_terminal` 重试在 Rust Agent 侧非幂等，会重复创建 shell

- **位置**：`src/index.js:1005-1010,1156-1172`；`agent/rust/src/main.rs:144-171`；`agent/rust/src/session.rs:37-52,85-87`
- **现象**：DO 在未收到 `terminal_ready` 时重发相同 SID；Agent 每次都重新 spawn PTY/bash，并用同一 SID 覆盖 Map 中旧项，却不停止旧进程。
- **影响**：网络延迟即可产生多个孤儿 shell；旧任务结束时还可能删除新会话 Map 项，造成进一步状态错乱。
- **修复建议**：Agent 对 SID 建立 `starting/active` 幂等状态；重复请求只重发 ready。任务结束时仅删除仍指向自己的 Map 项；DO 挂接新数据流时拒绝或关闭同 SID 旧流。

### H-06 文件上传无背压，500MB 文件可形成巨大内存/网络队列

- **位置**：`public/app.js:590-621`；`agent/rust/src/session.rs:187-199,319-365`
- **现象**：前端不等待 `write_result` 就连续读取、base64 编码并发送所有块，也不检查 `WebSocket.bufferedAmount`。Agent 串行写盘。
- **影响**：500MB 文件可产生约 667MB base64 数据及额外复制，慢盘/NFS 下浏览器、DO 和网络队列持续膨胀，导致标签页或会话崩溃。
- **修复建议**：采用 stop-and-wait 或有限滑动窗口；ACK 必须包含真实写入字节数和期望下一 offset；设置 `bufferedAmount` 高低水位；优先使用二进制帧。

### H-07 文件上传直接截断最终文件，失败会破坏原文件

- **位置**：`agent/rust/src/session.rs:319-365`
- **现象**：offset 0 时直接对最终路径 `set_len(0)`；解码、写盘、连接或超时失败后会留下截断/半写文件。超时仅停止等待 `spawn_blocking`，不能取消已运行的阻塞写任务。
- **影响**：覆盖配置、数据库或业务文件时可造成不可恢复损坏；超时重试还可能与后台旧写入并发。
- **修复建议**：使用同目录临时文件和 `begin/write/commit/abort` 协议；严格校验 offset、总大小和可选哈希；`flush + sync_all` 后原子 rename；断线清理临时文件。

### H-08 空 PAT 白名单在列表接口中被解释为“全部服务器”

- **位置**：`src/index.js:400-414,433-466,688-705`
- **现象**：创建 `server_ids: []` 后保存 `[]`；`queryServersForUser` 仅在数组长度非零时过滤，因此空数组返回全量服务器。单服务器接口的 `canAccessServer` 却拒绝所有服务器，语义不一致。
- **影响**：本意为“无服务器”的 PAT 可通过 `/api/servers`、PanelDO 和 MCP 枚举全量服务器及状态/系统信息。
- **修复建议**：仅 `NULL` 表示全部，空数组必须返回空集；创建时规范化并对 NULL、空数组、非法数组分别测试。

### H-09 登录端点无应用内限流，默认 `workers.dev` 暴露时可暴力破解

- **位置**：`src/index.js:488-500`；`README.md:235-236`
- **现象**：代码明确将防暴力破解完全交给 Cloudflare Access，但 README 只是“推荐”，部署步骤仍直接引导访问 `workers.dev`。
- **影响**：未配置 Access、WAF 或 Rate Limiting 的常见部署可被无限尝试面板密码；所有用户仅凭密码登录且拥有管理员权限。
- **修复建议**：应用层按 IP + 账户做 DO/Rate Limiter 限制和指数退避；部署文档将 Access 从“推荐”改为生产必需并给出验证步骤；增加失败阈值测试。

### H-10 Agent 默认以 root 运行，远程终端和文件管理等价于整机 root

- **位置**：`agent/cf-panel-agent.service:18-38`；`agent/rust/src/main.rs:144-185`
- **现象**：service 未设置 `User=`/`Group=`，systemd 默认 root。虽然配置了部分 sandbox，但为文件管理保留了广泛文件系统访问，终端直接启动交互 shell。
- **影响**：Agent key、管理员 JWT、Worker 或依赖链任一失陷都可直接获得主机 root 权限。
- **修复建议**：默认创建专用低权限用户；将“只监控”“受限文件”“root 终端”拆成显式权限档位；生产默认 `DISABLE_EXEC=1`，启用执行必须有醒目风险确认；进一步限制 capabilities、可写路径和命令范围。

### H-11 删除服务器与并发上报存在竞态，可重新生成孤儿指标

- **位置**：`src/index.js:346-395,588-622`
- **现象**：上报先读服务器，再更新/写 MetricsDO；并发删除可在清理后继续完成旧上报，重新写入热区或自定义指标。Schema 没有外键约束。
- **影响**：被删除服务器的数据可能被重新归档；ID 重用时可能污染新服务器历史。
- **修复建议**：服务器先原子标记 `deleting`，上报条件更新并在写 DO 前复核；断开 Agent 后二次清理。Schema 增加外键/不可复用稳定标识，避免仅以自增 ID 关联历史。

## 5. Medium

### M-01 `server:exec` PAT 可创建会话，但 WebSocket 首帧只接受 JWT

- **位置**：`src/index.js:625-662,1229-1237`
- **现象**：REST 使用 `authUserByToken/canExec` 接受 PAT；TerminalDO 首帧却调用 `verifyJwt`，PAT 必然以 1008 断开。
- **影响**：公开支持的 PAT exec 功能不可用，API 契约自相矛盾。
- **修复建议**：WS 使用 `authUserByToken` 并重新校验会话服务器的 `canExec`；或明确取消 PAT 的交互执行能力。

### M-02 任意 WebSocket 断开会取消整个分片的终端确认重试

- **位置**：`src/index.js:1339-1374`
- **现象**：`cleanup` 无论关闭的是浏览器、文件流还是某台 Agent，都无条件清空全部 `pendingTerm`。
- **影响**：一个无关连接关闭即可让其他服务器丢失终端重试。
- **修复建议**：pending 记录保存 SID/server/agent 归属，只清理关联项；增加跨 SID、跨服务器隔离测试。

### M-03 Agent 流尚未挂接时，浏览器终端输入被静默丢弃

- **位置**：`src/index.js:1298-1323`；`test/e2e.sh:192-199`
- **现象**：浏览器鉴权后立即输入，而 `sess.agentWs` 尚为空时没有缓存或错误。E2E 通过重复发送命令规避竞态。
- **修复建议**：增加有上限的 user→agent 缓冲，挂接后按序刷新；前端在收到 ready 前禁用输入或显示连接状态。

### M-04 离线创建失败的会话会写入内存/Storage，且不一定安排回收 alarm

- **位置**：`src/index.js:979-1011,1122-1147`
- **现象**：先保存 session，后检查 Agent 是否在线；返回 502 时未回滚。新会话也未统一安排 TTL alarm。
- **修复建议**：先确认 Agent，后持久化；所有失败路径回滚；每次创建都安排清理 alarm。

### M-05 Storage 扫描和 D1 batch 均无分页/批次上限

- **位置**：`src/index.js:1403-1419,1478-1503,1655-1680`
- **现象**：`storage.list({prefix})` 一次物化全部键；所有归档语句一次提交。
- **影响**：alarm 积压或服务器增多后，单次执行可能超过内存、CPU、D1 batch 或调用时长限制。
- **修复建议**：固定 limit + cursor 分页；每批完成“D1 成功→Storage 删除”；为单次 alarm 设置最大处理量并续排近时 alarm。

### M-06 历史归档永久丢弃 `mem_total`

- **位置**：`schema.sql:43-53`；`src/index.js:1430-1439,1665-1674`
- **现象**：热区保存 `mem_total`，`metrics_min` 没有该列，归档和历史查询也不返回。
- **影响**：历史数据无法按当时总内存计算百分比，扩容后统计失真。
- **修复建议**：增加 D1 迁移列并同步归档/查询。

### M-07 告警冷却与探活状态仅在内存，重启后重复或漏发

- **位置**：`src/index.js:1382-1393,1533-1612`
- **现象**：`alertLast`、`probeState` 在 DO 重启时清空；离线状态则持久化，行为不一致。
- **影响**：重启后重复阈值告警、重复 probe_down，或漏掉 probe_recovered。
- **修复建议**：将关键去重状态持久化到 DO Storage，并设置合理过期时间。

### M-08 Webhook 失败被吞掉，且先更新去重状态

- **位置**：`src/index.js:321-340,1541-1545,1586-1612,1621-1644`
- **现象**：不检查 HTTP 状态，网络异常被吞；告警状态在发送成功前已经更新。
- **影响**：发送失败后仍进入冷却或离线已通知状态，关键告警不会重试。
- **修复建议**：`sendWebhook` 返回成功状态并检查 `response.ok`；发送成功后再提交去重状态，重要告警使用持久化 outbox。

### M-09 `sanitizeAlerts` 接受 PUT，但发送函数会静默改成 POST

- **位置**：`src/index.js:149-178,321-339`
- **现象**：配置允许 GET/POST/PUT，发送时仅 GET 保留，其余都使用 POST。
- **修复建议**：统一允许列表和执行逻辑，并为三种方法增加测试。

### M-10 大文件下载在浏览器中多次复制整文件，峰值内存可超过 1.5GB

- **位置**：`public/app.js:549-587`
- **现象**：保存所有二进制字符串分块，完成后 `join`，再复制到完整 `Uint8Array`，最后构造 Blob。
- **影响**：400–500MB 文件很容易使低内存浏览器卡死或崩溃。
- **修复建议**：流式写 File System Access API/StreamSaver；至少每块立即转 `Uint8Array` 并直接 `new Blob(parts)`，同时降低非流式上限。

### M-11 下载期间文件缩短时可能无限读取 `got=0`

- **位置**：`public/app.js:558-587`；`agent/rust/src/session.rs:272-309`
- **现象**：前端以初始 size 为终止条件；文件中途缩短时 Agent 可持续返回成功且 `got=0`，前端不断请求相同 offset。
- **修复建议**：`got===0` 且未完成时中止；响应携带当前文件 size/版本，客户端校验 offset 单调增长。

### M-12 Agent 接受明文 `ws://` 配置，Agent key 可被窃听

- **位置**：`agent/rust/src/main.rs:37-49,88-96,252-260`
- **现象**：帮助文档推荐 `wss://`，运行时未验证 scheme；key 作为 `X-Agent-Key` 发送。
- **影响**：误配置明文连接时，网络中间人可获取长期 Agent 凭据并接管终端/文件通道。
- **修复建议**：默认仅允许 `wss://`；本地开发需显式 `ALLOW_INSECURE_WS=1` 且只允许 loopback。

### M-13 Rust Agent 没有测试，正式 Release 仅要求编译成功

### M-15 D1 缺少版本化迁移，README 的旧库升级流程不完整

- **位置**：`package.json:14-16`、`package-lock.json`
- **验证结果**：`npm audit` 报告 3 项：1 high、2 moderate。核心为 `undici 7.0.0–7.28.0`，经 `miniflare`/`wrangler` 引入，包括信息泄露、解析崩溃和请求解析差异类公告。

### M-17 CI/Release 供应链固定不足

### M-18 前端将服务器公网 IP 发给第三方地理服务

- **修复建议**：默认关闭或明确提示；改为服务端可控代理/离线数据库；提供隐私开关和文档说明。

## 6. Low

### L-01 浏览器 token 存在 `localStorage`，且项目未设置 CSP 等安全响应头

- **位置**：`public/app.js:6,74-86`；`src/index.js:74-78`；`public/index.html`

### L-02 每次打开终端都会注册匿名 window resize 监听器，关闭时无法移除

- **位置**：`public/app.js:396-402,467-470`
- **影响**：多次打开/关闭终端后累积监听器，造成不必要调用和内存泄漏。
- **修复建议**：保存 handler 引用，在 `close()` 中 `removeEventListener`。

### L-03 文件目录列表没有条目数和响应大小上限

- **位置**：`agent/rust/src/session.rs:240-269`
- **影响**：列出超大目录会物化全部条目、生成巨大 JSON；超时不会取消已开始的 `spawn_blocking` 操作。
- **修复建议**：分页、最大条目数和续页 token；对超时阻塞任务设置更可靠的隔离方式。

### L-04 Schema 缺少外键和唯一性约束

- **位置**：`schema.sql:22-64`
- **说明**：PAT、审计、系统指标和自定义指标仅用整数关联服务器/用户，没有 FK 或稳定 UUID；`api_tokens.token_hash` 也未显式 UNIQUE。
- **建议**：结合 D1 支持情况增加约束与索引；至少通过迁移和清理任务维护引用完整性。

### L-05 弹窗可访问性不足

- **说明**：弹窗使用普通 `div`，缺少 `role="dialog"`、`aria-modal`、焦点陷阱、Esc 关闭和关闭后焦点恢复。

## 7. 前端专项结论

### 做得好的点

1. 对服务器名、分组、系统信息、探活名、文件名、审计详情等动态 HTML 均使用 `escapeHtml`；本次未确认到可直接利用的 DOM XSS。
2. WebSocket token 不放 URL，避免出现在浏览器历史、代理日志和常规访问日志中。
3. xterm.js、Chart.js 已本地化，避免运行时依赖外部 CDN。
4. REST 封装统一检查 HTTP 状态，敏感新增凭据只显示一次。
5. 监控图表有前端降采样，避免长区间直接渲染过多点。

### 主要改进方向

- 文件传输必须改为有状态、可确认、可恢复且原子的协议，而不是继续在前端修补进度显示。
- token 生命周期和安全响应头需要进入安全基线。
- 增加真实浏览器测试：终端 ready 竞态、上传断线、下载文件变化、重复打开弹窗、键盘可访问性。

## 8. Worker 后端专项结论

### 做得好的点

1. Agent key 使用 SHA-256 指纹定位 + HMAC 哈希校验，避免明文落库。
2. PAT 支持 scopes 和 server_ids，主 API 大部分路径都有权限复核。
3. 终端/文件浏览器 WebSocket 使用首帧鉴权，token 不进入 URL。
4. MCP 有 Origin 校验，并复用 API 权限过滤。
5. 监控查询和审计 limit 有边界，长区间有 SQL 侧抽样。
6. TerminalDO 已将会话元数据持久化，并有 Hibernation/TTL 思路。

### 其他协议问题

- `src/index.js:837-880` 的 MCP/JSON-RPC 未完整验证 `jsonrpc: "2.0"`、batch 与标准 notification 语义，协议版本协商也没有完全使用标准 `params.protocolVersion`。建议以官方 conformance fixture 补测。
- 审计目前只覆盖服务器创建/删除和“打开”终端/文件会话；PAT 创建删除、设置修改、文件读写、登录失败等高价值事件没有完整记录。远程管理面板应补充结构化安全审计，但避免默认记录终端命令内容。
- 多用户登录只提交 password；若两个用户使用相同密码，`findIndex` 固定命中第一人，身份与审计归属错误。应要求 username + password，并使用恒定时间密码验证/成熟身份提供方。

## 9. Rust Agent 专项结论

### 做得好的点

1. 文件 WS 有单消息 8MB 限制，单次读取限制为 512KB，解码缓冲固定为 64KB。
2. 大部分同步文件/系统命令通过 `spawn_blocking` 移出 async runtime。
3. 自定义命令使用独立进程组并启用 `kill_on_drop`，减少超时孤儿进程。
4. systemd 已启用 `NoNewPrivileges`、`PrivateTmp`、内核/控制组保护和地址族限制。
5. 系统命令使用参数数组调用，没有发现把 Agent 上报数据拼入 `sh -c` 的路径；`sh -c` 仅用于管理员显式配置的自定义指标。

### 主要改进方向

- 首先解决 root 权限边界、会话配额、重复 SID 幂等和文件原子写。
- 加入 Rust 单元测试与协议集成测试；当前 Worker 测试无法证明真实 Agent 行为正确。
- `blocking_with_timeout` 只是超时停止等待，不能终止同步 I/O；注释不应把它描述成已防止后台阻塞任务持续运行。

## 12. 建议验收标准

- 所有 Critical/High 问题均有可失败再修复的自动化回归测试。

## 14. Cloudflare 额度消耗分析

> **计量口径（2026-08-04 官方文档）**：Workers Free：10 万请求/天、CPU 10 ms/请求、D1 5M 行读 + 10 万行写/天、存储 5GB；Durable Objects Free（SQLite 后端）：10 万事件/天、13,000 GB-s/天、DO Storage 5M 行读 + 10 万行写/天、存储 5GB。DO 的 HTTP 请求、alarm、Worker 到 DO 的 `stub.fetch` 与 WebSocket 消息都计入事件；入站 WS 消息按 20:1 折算为计费请求，连接建立另计 1 次；Hibernation 休眠不计时长，事件处理期间按 128MB 墙钟计费。Workers Assets 与出站流量不计上述额度。
>
> **基线参数**：`S` = 服务器数，`V` = 同时在线观看者数，`C` = 每机自定义指标数。Agent 有观看者时 3 秒上报（28,800 帧/天/机），无人观看时 120 秒上报（720 帧/天/机）；Panel 前端每观看者 3 秒发一次 `sync`（28,800 帧/天/人）；Metrics alarm 每 10 分钟一次（144 次/天）。行号均指当前 `src/index.js`。

### 14.3 主要瓶颈结论

1. **DO 免费事件档是唯一最现实的超支点**：快采 Agent（3 事件/帧）与 Panel sync（2 事件/次）共同导致 1 台机 1 观看者全天约 14.4 万事件，已超过 10 万/天。
2. **D1 `last_seen` 是最大且最容易削减的写入源**：快采 28,800 行/天/机，但在线宽限期为 15 秒，实际不需要每秒落盘。
3. **alarm 当前实现存在两层浪费**：每 10 分钟全量 `list('m:')` 读 `720×S` 行；对 60min~12h 已归档行重复 `INSERT OR IGNORE`，免费档下可能把本用于真正写入的行写额度消耗掉。
4. **Panel sync 的 D1 成本随 `S×V` 放大**：每观看者每 3 秒重新鉴权、读 PAT（若使用）并全量读取服务器。
5. **MetricsDO `/latest` 已比旧实现安全**：只在 `this.data.size===0` 时全扫 storage（`1701-1717`），避免面板 3 秒轮询常态全扫；但 evict 后仍有一次 `720×S` 行尖峰，且没有增量 latest 结构。
6. **Hibernation 使用方向正确**：Agent/Panel/Terminal 长连接在空闲时不会按整个连接时长计费；成本主要来自消息事件和处理墙钟，不是连接数本身。

## 15. 在保证安全与正确前提下的降额优化

> 优先级按“收益/改动复杂度/正确性风险”排序。P0/P1 均不改变鉴权、权限边界、数据保留语义或 Agent 协议；不要求删除 DO，目标是让现有架构在免费档内更久运行。

### 15.1 P0：直接解决最可能超限的路径

1. **alarm 改为增量归档与逐行清理** ✅ 已实施（2026-08-05）：`/report` 热写路径按归档水位 `arc:{serverId}` 增量归档（跨线行直接归档 + 水位区间批量），D1 成功后才推进水位；`alarm()` 仅做离线告警/保留期清理，全量 `fullSweep` 降频为每 6 次（≈1 小时）执行（>12h 行清理 + 兜底归档），DO Storage 读约 `103,680×S` → `~17,280×S`/天，重复 INSERT 基本消除。**修复（同日）**：水位改为只推进到本次实际归档的最大 `ts`（不再无脑推进到归档线），区间扫描限 `METRICS_KEEP_MIN` 次（≤720/帧）——修复热写免 loadHot（#8）引入的 evict 后空 Map 导致「storage 历史行被水位越过 → fullSweep 永久跳过 → 12h 删除 → 3d/7d/30d 历史空洞」回归，以及新服务器 `arcTs=0` 从分钟 1 空循环约 4000 万次的 CPU 尖峰；未覆盖区间由 `fullSweep` 全扫兜底（含回归测试）
   - 当前：`alarm()` 每 10 分钟全量 `list('m:')`，并对 60min~12h 已归档行重复 `INSERT OR IGNORE`（`1892-1955`）。
   - 建议：`/report` 写入内存热区时，直接对本次内存 Map 中 `ts <= archiveCutoff` 的少量行做 D1 `INSERT OR IGNORE`、对 `ts <= keepCutoff` 的键直接删除；持久化每台机的归档水位（如 `arc:{serverId}=lastArchivedTs`）。`alarm()` 只执行离线告警、保留期清理和低频兜底，不再常态全扫 720×S 行。
   - 预期：DO Storage 读约 `103,680×S` → 数百~数千行/天；重复归档查询约 95,000 条/天/机 → 增量后实际新增约 10 条/10 分钟；alarm 时长显著下降。
   - 正确性约束：D1 成功后再删除 Storage；水位仅作加速，不替代 D1；evict 后从水位恢复并允许重复 `INSERT OR IGNORE` 兜底。

   - 正确性约束：PAT 删除必须即时失效；服务器权限过滤仍在每条响应前检查；缓存只作用于静态列表，不缓存 `canAccessServer` 结论到可越权对象。

### 15.2 P1：显著降低免费档压力

5. **MetricsDO `/latest` 使用增量 latest Map** ✅ 已实施（2026-08-05）：`/report` 热写 O(1) 维护 `latestByServer`（含秒级 `last_seen_s`），`/latest` 直接 O(S) 返回；仅实例 evict 后（增量 Map 为空）全扫 storage 恢复并回填。`/drop` 同步清理增量项

### 15.3 P2：规模更大时的容量与延迟优化

11. **终端/文件输出批量合帧** ✅ 已实施（2026-08-05，Rust agent）：PTY 输出聚合 `TERM_BATCH_MS=16ms` 或 `TERM_BATCH_BYTES=32KB` 合并一条 WS 帧（刷屏时 DO 计费消息约 −60%~75%，交互延迟 ≤16ms 无感、顺序保持）；文件 `READ_BLOCK` 512KB → 1MB 与前端下载分块对齐（一次 read 返回 1MB，下载帧数 −50%；前端按 `got` 自适应续传，兼容）
    - 当前：Rust Agent PTY 每 8KB 一帧，文件下载 512KB 一轮；每条入站帧按 20:1 计费。
    - 建议：Agent 按 10~20ms 或 32~64KB 聚合输出；文件 `READ_BLOCK` 与前端 1MB 块对齐。
    - 预期：刷屏/大文件传输的计费消息数约降 50%~75%；注意文件协议的正确性应优先于合帧。

12. **MCP/API 列表复用 PanelDO 缓存** ✅ 已实施（2026-08-05）：抽取公共 `listServersWithState(env, user)`（`/api/servers` 与 MCP `list_servers` 共用），按用户维度 2s TTL 短缓存（权限过滤仍在 SQL 层，不缓存越权结论；服务器增删改时显式 clear，最长滞后 2s）；多入口不再各自读 D1 全表 + `/latest` + `/viewers`
    - 当前：`/api/servers`、MCP `list_servers` 都单独读取 D1、`/latest` 和 `/viewers`（`664-677`, `884-920`）。
    - 建议：低风险场景沿用短 TTL 列表缓存，或抽公共读取函数；MCP 可支持分页/摘要，避免 AI 客户端循环拉全量。
    - 预期：多入口重复读降低；对免费 Worker/DO 额度更友好。

13. **离线告警只在需要时调度** ✅ 已实施（2026-08-05）：未配置 `webhook_url` 时直接跳过离线扫描（零成本）；在线判定复用增量 `latestByServer` 秒级 `last_seen_s`（与列表判定一致）；离线状态一次性 `list('alert:offline:')` 惰性加载到内存，不再逐机 get（S 大时免 144×S 行读）
    - 当前：告警开启时 alarm 每 10 分钟读全部 servers 并逐机读取离线状态（`1856-1888`）。
    - 建议：离线判定直接利用上报路径和 MetricsDO latest；alarm 在未配置 webhook 时跳过离线扫描；离线状态加载采用一次性 list 并按 server 惰性恢复。
    - 预期：S 大时减少 144×S 行 D1/storage 读/天；未配置告警时几乎零成本。

14. **保留期与存储增长预警** ✅ 已实施（2026-08-05）：`METRICS_RETENTION_DAYS` 支持环境变量覆盖（默认 30，缩短线性降容量）；前端自定义指标设置弹窗加容量提示（每机 ≤20 个，占用 ≈ 43,200×S×C 行）；README 新增「免费额度与容量估算」小节（含公式与 `/api/usage` 入口）

    - 建议：在设置页展示近 24 小时的估算用量：DO 事件（上报帧、sync 帧、alarm）、D1 读写行、DO Storage 读写行；至少通过日志/Admin API 定期统计。
    - 预期：部署者在多 Worker 共享免费额度时能提前发现 cf-panel 占额异常，而不是超限后服务失败。

### 15.4 不建议的“省费”方式

1. **不建议把热区彻底迁回 D1**：每次上报 D1 写行与读行会立即把免费写档击穿，正确性和成本都更差。
2. **不建议取消 alarm**：alarm 仍承担离线告警、保留期清理与兜底归档；应改为增量和低频兜底，而不是删除。
3. **不建议删除 DO Hibernation 或改长轮询 HTTP**：长轮询会产生更多 Worker/DO 请求和墙钟时长，成本更高。
4. **不建议为省行数删除审计或弱化鉴权**：安全与权限边界优先级高于额度；可用缓存和事件驱动降耗。
5. **不建议默认降低上报到分钟级**：会改变实时面板体验；应先做事件驱动调度、缓存和增量归档。

### 15.5 优化后的目标量级（实施 P0 后估算）

- 1 台机快采 + 1 观看者全天：DO 事件约 **9 万/天以内**（report 2 事件 + sync 2 事件），回到免费档边缘；若再做后台标签页暂停，常态明显更低。
- D1 写行：last_seen 约 **5,760 行/天/机**，指标约 1,440 行/天/机，重复归档基本消除；5 台快采可从 >15 万/天降至约 3.6 万/天。
- DO Storage 读：alarm 全扫从 `103,680×S` 行/天降为增量读取；`/latest` evict 尖峰消除。
- 结论：在不牺牲鉴权、权限过滤、原子写、幂等重试与监控正确性的前提下，P0 四项即可把最主要的 DO/D1 免费档压力降低约 40%~70%，P1/P2 进一步为多 Agent、多观看者和多 Worker 共账户部署留出余量。
