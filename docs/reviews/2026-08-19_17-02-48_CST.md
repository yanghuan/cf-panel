# Rust Agent 专项 Review：性能 / 内存 / IO 异常与超时（2026-08-19）

> **对象**：`agent/rust/src/`（main.rs 949 行、session.rs 1,423 行、metrics.rs 921 行，共 3,293 行）+ `Cargo.toml`（构建优化注释一并复核）。HEAD=`ca0f5f5`

## 1. 总体评价

整体设计成熟度高于一般 agent 实现：有界通道 + 丢弃降级（日志）、三级入站消息上限（控制 64KB / 终端 1MB / 文件 8MB）、blocking 信号量限流（4 permits）、磁盘采集 60s 缓存 + 失败真熔断、终端合帧（16ms/32KB，DO 计费消息数降 60~75%）、重连退避健康度判定（≥10s 才重置 + 抖动 + 401 长退避）、exec 进程组清理（`kill(-pid)` 防孤儿）、原子写（临时文件 + fsync + rename + 严格 offset 校验）、symlink 写穿双层拦截（词法 + canonicalize）。多轮 review 沉淀的注释体系（每个优化点写明原理、边界与取舍）保持了既有水准。

本轮发现集中在**同一个主题的遗漏面**：设计者为「正常路径」建立了完善的超时/限流体系，但存在三条**绕过该体系的路径**（控制通道上传裸 spawn_blocking、PTY 写入、数据面连接），以及若干超时体系本身覆盖不到的边界（DNS 解析在 timeout 作用域外、spawn_blocking 线程不可取消、take 截断后管道满）。以下按严重度列出。

## 2. High：超时缺失 → 永久挂死 / 线程饥饿

### H1 控制通道上传路径无超时、不受信号量限流，可永久卡死读循环

`main.rs:358` 的 `handle_upload_frame` 直接裸 `tokio::task::spawn_blocking`，**无超时、不占 4-permit 信号量**——而文件会话的同语义路径 `handle_file_cmd_binary`（session.rs:873）走的是 `blocking_with_timeout(30, ...)`。`write_bytes` 内部会执行 `canonicalize` + 磁盘写（其注释自述「canonicalize 阻塞由外层超时兜底」，session.rs:1116），但这条路径恰恰没有外层超时。

致命点在于读循环的超时只包住 `read.next()`（main.rs:240-268）：`handle_upload_frame` 在超时作用域**之外**被 await。挂死挂载点（NFS 等）上执行上传 → blocking 任务挂死 → 读循环永久阻塞，且：

- 180s 半开检测不触发（不在 `read.next()` 里）；
- 心跳 ping 收不到（不读则 tungstenite 不会自动回 pong，服务端侧也会判定 agent 死亡，但 agent 自身无感知）；
- `set_report_interval` / `open_terminal` / `open_file` 等所有后续指令全部失效；
- agent 表现为「假活」：进程在、CPU 空、永远不恢复，只能重启。

**修复**：与文件会话对齐改用 `blocking_with_timeout(30, ...)`（顺带纳入信号量，堵住「上传绕过限流」的旁路）。

### H2 PTY 写入在 async worker 上执行阻塞 IO，多会话可饥饿 runtime

`session.rs:249-258`：`writer` 是 `std::io::Write`（阻塞），`write_all` + `flush` 直接在 tokio worker 线程执行（且持有 tokio Mutex）。PTY 输入缓冲有限（典型 ~4KB），以下场景 `write_all` 会阻塞到子进程消费为止：

- 用户 Ctrl+S（XOFF 流控）后 shell 停止读输入；
- 全屏 TUI 程序暂停消费 stdin；
- 子进程任何原因不读 stdin 但持续运行。

`TERM_MSG_LIMIT` 允许单帧 1MB——一次大粘贴即可让 worker 阻塞数秒以上；多个此类会话并发即可占满全部 worker 线程，**整个 runtime（含控制通道、采集、其它会话）饥饿**。读路径已经做了对称设计（专用 OS 线程 + channel，session.rs:187-199），写路径却裸奔在 worker 上，属明显不对称。

**修复**：输入同样走专用线程/通道（与 reader 对称），或至少 `spawn_blocking` 包裹；进一步可考虑批量合并输入写（terminal 输入帧通常极小，合并收益可观）。

### H3 终端/文件数据连接无空闲超时，半开连接下会话/子进程/fd 永久泄漏

控制通道有 180s 读超时做半开检测（main.rs:242），但两条数据面连接都没有：

- 终端：`session.rs:240-263` 的 select 循环无 timeout；
- 文件会话：`session.rs:302` 的 `while let Some(msg) = read.next().await` 无 timeout。

NAT 静默丢链（映射表项过期，无 FIN/RST 到达）+ 子进程无输出（idle shell）时：读不到 EOF、发送也无数据可发 → 连接永久挂起 → PTY fd、子进程（bash 进程组）、sessions map 条目、reader 线程、合帧任务全部泄漏。若子进程恰好有输出会在发送时发现错误并自愈，但 idle 场景（恰恰是终端最常见的状态）无解，只增不减直到 agent 重启。

**修复**：数据面 `read.next()` 套长空闲超时（如 10~15min 无任何入站消息即断开清理）。注意半开下 `Notify`/心跳类机制无效（出站也会静默失败而不报错），纯入站空闲计时是可靠且零成本的方案。

## 3. Medium：内存峰值 / 帧率 / 线程池健康

### M1 zip 全内存物化，峰值内存 ≈ 目录大小 × 2，小内存 VPS 有 OOM 风险

`session.rs:621-627`：`zip_directory` 把整个 zip 累积进 `Vec<u8>`，且每个文件先 `fs::read` 整个读进 `data`（session.rs:515）再 append 后丢弃。`walk_dir_size` 预检上限 500MB，但峰值 = `out` 累积（≤500MB）+ 当前正在处理的单文件（最大也可 500MB）≈ **1GB**。512MB 内存的 VPS 上打包一个 300MB 目录（含单个 300MB 大文件时）即可能触发 OOM killer——而 agent 被 OOM 杀死会连带杀掉所有终端会话。

**修复**：流式写临时文件——`BufWriter<File>` 顺序写 local header + 数据，CRC 用固定块（如 64KB）增量计算，central directory 单独累积（通常很小，条目名级别），最后 seek 回填或追加写 EOCD。内存占用从 O(目录大小) 降为 O(1)。

### M2 探活/自定义指标串行执行 + DNS 解析不设超时，快采帧率被稀释

- `metrics.rs:614-645`：N 个探活**串行** await，http 探活各自 5s 超时 → 最坏 5N 秒；自定义指标同理（`collect_custom` 串行，5s/个）。5 个探活 + 3 个自定义指标最坏 40s，远超快采间隔 5s——`report_loop` 的实际帧率被采集时长绑架，有观看者时「5s 上报」承诺失效。
- `http_probe`/`tcp_probe` 中 `tokio::net::lookup_host`（metrics.rs:553、592）在 `timeout(...)` 作用域**之外**：glibc resolver 默认 5s 超时 × 2 次尝试，DNS 故障时每个探活额外多挂 10s+ 且**无上界**（timeout 只包住 connect + 请求）。

**修复**：探活与自定义指标 `join_all` 并行（各自仍有超时上限，总时长 = max 而非 sum）；DNS 解析包进 timeout。

### M3 挂死的 blocking 线程不可回收，文件操作无熔断 → 线程池缓慢耗尽

`blocking_with_timeout` 的超时只是「放弃等待」，spawn_blocking 线程本身（挂在 NFS statvfs/read 上）**无法取消**，会永久占用。现状：

- 磁盘采集有 60s 熔断兜底（metrics.rs:198-208），最坏每 60s 泄漏 1 个线程；
- **文件操作没有任何熔断**：挂死挂载点上前端每次重试（上传/删除/read）都在 30s 超时后泄漏一个新线程。操作员反复重试 + 前端自动重试放大，数小时内即可耗尽 tokio blocking pool（默认 512 线程）——届时 `uname`/`hostname`（采集）、全部文件操作排队，agent 功能整体瘫痪（但进程仍在，与 H1 同样表现为假活）。

**修复**：文件操作路径复用磁盘采集的熔断模式（同一路径连续失败后短期熔断返回错误），激进方案是路径操作子进程化（超时可 kill）。

### M4 exec 大输出命令被误报为 timeout（take 截断 + 管道满阻塞子进程）

`main.rs:618-644`：stdout `take(48KB)` 读满后 `read_to_end` 返回 EOF，但子进程仍在写——管道缓冲（Linux 默认 64KB）写满后子进程**阻塞在 write() 上永不退出**，`child.wait()` 挂到整体超时。输出超过 ~112KB（48KB take + 64KB pipe）的命令（`grep -r`、`find /` 等）一律命中：用户看到 `timed out after Ns` + **空 stdout**，而不是截断后的前 44KB——超时语义被污染，且拖满整个 `timeout_s` 窗口。

**修复**：take 限额读满后继续 drain（循环读并丢弃），让子进程能自然退出，`wait()` 正常返回后按截断语义上报。

## 4. Low：加固与维护项

- **L1 cleanup 的阻塞 wait 在 async 上下文**：session.rs:112 `c.wait()` 是 portable-pty 的阻塞 wait，kill 后通常立即返回，但 D 状态子进程会挂住 worker；shutdown 路径（main.rs:836-839 顺序 cleanup）会被一个 D 状态会话挂住整个退出流程。建议 `spawn_blocking` 包裹。
- **L2 exec 超时后 `child.wait().await` 可永久挂起**：main.rs:665，D 状态进程收不到 SIGKILL；任务泄漏（不持锁、DO 有兜底定时器，影响小）。该 child 也未设 `kill_on_drop`。给 wait 加短超时即可。
- **L3 持锁跨 await**：main.rs:439-453（open_terminal 幂等分支）与 492-500（open_file）在持有 sessions/file_sessions 锁期间 `w.send().await`——控制通道拥塞时所有会话操作（resize 等）被连坐阻塞。把 send 移出临界区（先 clone 判定结果，锁内只做 get/remove/insert）。
- **L4 `failed.lock().unwrap()` poison 即 panic**：main.rs:321、337、343、349、373。理论上几乎不可能 poison（临界区内无 panic 路径），但 async 读循环里 panic 会杀进程，与其余处的容忍式处理（`if let Ok`）不一致，建议统一。
- **L5 PTY spawn 是同步 fork/exec**：`TermSession::spawn` 虽为 async fn 但全同步体（openpty + spawn_command），内存紧张时 fork 可达几十 ms，直接阻塞 worker 与控制读循环。可 `spawn_blocking`。
- **L6 读线程分配与合帧容量丢失**：session.rs:193 每读 8KB `to_vec()` 一次分配；session.rs:208 `mem::take` 后 batch 容量归零反复 realloc。量级小（背压上限 64×8KB=512KB/会话），微优化：复用缓冲/发送后 `reserve`。
- **L7 日志写线程每行一次 `f.metadata()`**：main.rs:121，每行日志一次 fstat 系统调用。写线程自行累计已写字节即可。另注意：stdout 管道对端不消费时会阻塞写线程，**文件日志也随之停摆**（同线程顺序执行）——丢弃降级设计可接受，但「文件日志不受 stdout 影响」更稳。
- **L8 `count_lines` 同步读大 `/proc/net/tcp`**：metrics.rs:155。50 万连接时是几十 MB 文本同步读在 worker 上（BufReader 已避免物化整串，值得肯定），可 `spawn_blocking`。
- **L9 注释与实现不符 + 双套 blocking 包装**：metrics.rs:750 注释称「blocking 峰值 = info(1) + disk(1) = 2 < Semaphore 4」，但 `collect_disk`（metrics.rs:191）实际裸 spawn_blocking 不走信号量，只有 info 走；且 metrics.rs `run_blocking` 与 session.rs `blocking_with_timeout` 是两套重复实现、两个独立 4-permit 信号量。建议合并为一处（公共模块）并修正注释，避免后来者按错误注释继续堆路径。
- **L10 tungstenite 0.21 偏旧**：当前 0.24+ 有若干修复（含握手/协议边界）。择机升级，注意 `WebSocketConfig` 字段与 `Message` 枚举 API 变化。

## 5. 复核通过项（本轮重点维度）

以下为按本轮关注点复核**确认有效**的设计，供后续维护对照：

1. **内存上限体系**：控制 64KB / 终端 1MB / 文件 8MB 三级 `max_message_size`；exec 有界读取 48KB/16KB + 截断 44KB/12KB（UTF-8 边界安全）；列表 1000 条截断；上传 500MB 硬上限（临时文件长度校验）；EOCD 65535 条目显式报错不截断。
2. **合帧逻辑正确性**：TERM_BATCH 16ms/32KB 合帧的状态机推演无误（超时 flush、满量即发、通道关闭 flush 后退出、顺序保持），DO 计费收益真实。
3. **退避体系**：指数退避 3s→300s + 0~50% 抖动 + 401 长退避 + ≥10s 健康度重置，秒断风暴与重连风暴两个方向都覆盖到。
4. **磁盘熔断**：60s 缓存命中（快采 12 帧只跑一次）+ 失败真熔断（含「无旧值写空缓存」防开机即挂死场景空转）。
5. **exec 进程组语义**：`process_group(0)` + 超时 `kill(-pid)` 连孙进程清理，与终端 cleanup 语义一致。
6. **背压设计**：日志 mpsc 1024 有界 + `try_send` 丢弃（采集路径永不因日志挂起）；终端 reader channel 64 条有界（背压上限 ~512KB/会话）。
7. **join! 并行采集**：mem/load/conns/net/info/probes/custom/disk/disk_io 十项并行，串行累积已消除（剩余问题见 M2 的**内部**串行）。
8. **symlink 双层拦截**：词法层（`is_system_path`，fail closed）+ 真实路径层（`is_system_path_resolved`，防静态符号链接写穿），两条写入路径（WS write / 控制通道 upload）在 `write_bytes` 汇聚统一拦截，测试覆盖完整。
9. **原子写**：临时文件 `{path}.upload.{id}` + offset 严格校验（防丢块/乱序）+ commit 时 fsync + rename；会话结束/断线清理临时文件（含控制连接级清理）。

免费档容量对照（Workers Free：D1 100k 行写/天、5M 行读/天）：**~30 台机器在写额度内**；W-M1 修复前配探活的机器每台额外 +6,240 行写/天（见下），约 11 台即打满写额度（100k ÷ (2,880 基线 + 6,240)，2026-08-20 复核修正：原文 16 台漏加基线，保守方向）。

### 11.3 Medium 发现

#### W-M1 probe_json「变更才写」被 ms 抖动击穿，快采时每帧一次 D1 UPDATE

`report.js:99-107` sanitize 保留探活 `ms` 字段 → `report.js:157-161` 用**全量 JSON 序列化对比**判定变更。探活耗时 ms 每次探测必然不同（毫秒级抖动）→ 每帧 `probeJson` 恒不等 → 快采时段**每 5s 一条 `UPDATE servers SET probe_json`**：6,240 行写/天/机，是 D1 写基线 2,880 的 2.2 倍（单看 servers 表为 1,440 预期的 4.3 倍）。「变更才写」对 probes 完全失效，仅对 info_json（OS/内核稳定不变）有效。

**修复建议**：对比时剥离 ms——用 `{name, ok, code}` 稳定投影对比，ms 变化不触发写（前端探活延迟展示改为跟随 latest 推送或接受停更）；或对 probe_json 写做 60s 节流（与 last_seen 同模式）。测试补充：连续两帧仅 ms 不同 → 断言无 UPDATE。

#### W-M2 PAT 观看连接的鉴权缓存与推送节拍同频，每 5s 一拍 D1 读

`LATEST_PUSH_INTERVAL_MS=5000`（do-metrics.js:13，PanelDO 侧节拍常量）与 `authUserCached` 的 5s TTL（do-panel.js:35）**精确同频**：每拍 latest_push 到达时缓存恰好过期 → PAT 连接（第三方监控面板用 PAT 连 `/ws/push` 的场景）**每 5s 必 miss 一次 api_tokens 点查**（JWT 用户走 HMAC 零 D1 不受影响）。全天挂机的 PAT 连接 = 17,280 行读/天/连接。

**修复建议**：authCache TTL 延长至 30-60s。安全性论证：PAT 撤销已有**主动清理链路**（`routes.js:523` revoke → `clear_auth_cache` RPC → latest_push 时 user==null 即 close 连接），5s TTL 只是兜底而非主路径，延长后撤销生效仍秒级（RPC 即时）。listCache 4.5s / latestCache 4s 的**错峰设计**（防同频 miss）在 authCache 上被遗漏——同一设计原则下的疏漏。

#### W-M3 audit_logs 筛选查询无 action/server_id 索引，WHERE 过滤全表扫

`schema.sql:50` 仅有 `idx_audit_logs_created`（created_at）；而审计查询（`routes.js:539-568`，MCP 同款 `routes.js:967-974`）按 `action = ?` / `username LIKE` / `target_server_id = ?` 过滤 + `ORDER BY id DESC LIMIT/OFFSET` + **每请求两条查询**（rows + `COUNT(*)`）。90 天保留 × 操作量（如 500 条/天 = 45,000 行）→ 每次筛选请求 ~90,000 行读；管理员翻 20 页 ≈ 1.8M 行读（免费 5M/天的 36%）。`username LIKE '%x%'` 前导通配无法索引；action/server_id 精确匹配可索引。

**修复建议**：加 `idx_audit_logs_action` 与 `(target_server_id, id)` 联合索引（新增迁移文件）；COUNT 可用近似（`id > 上次最大 id` 增量）或短 TTL 缓存规避。当前量级免费额度内，配额敏感部署优先修。

#### W-M4 单 MetricsDO 实例的容量与扩展边界（记录，非缺陷）

MetricsDO 为单实例（`idFromName('main')`，`utils.js:205`）。内存：每机热区 720 分钟行 × ~400B + latest ~1KB ≈ 300KB/机 → 128MB DO 内存限下**理论上限 ~400 机**（留余量按 ~200 机规划）。冷启动：实例 evict 后首个 `/latest` 触发 `listStorage('m:')` **全量扫描 S×720 行**（do-metrics.js:317），200 机 = 144,000 行一次（秒级、一次性、已回填缓存避免重复放大）。TerminalDO 已有 4 分片模式可复制。**当前规模完全健康**；接入 >100 台时按 serverId 分片 MetricsDO 应提上日程（分片后 latest_push/viewers 聚合需相应改造）。

### 11.4 Low 发现

- **W-L1 read_result 帧理论上限超 CF WS 1MB 消息限制**：agent `READ_BLOCK=1MB`（session.rs:16）+ JSON 头 ~100B > 1,048,576——仅 `limit=0`（读全文件）或 `limit≥1MB` 的调用方触发（帧被拒/断连）。前端固定 `FILE_CHUNK=512KB`（api.js:8，注释已自知对齐 workerd 限制）不触发。建议 `READ_BLOCK` 留头余量（如 1MB−1KB）并注释协议上限。
- **W-L2 agent 每次重连的固定成本**：Worker 路由 D1 SELECT（routes.js:1208）+ DO 内再 SELECT（do-terminal.js:209）= 2 行读；DO 内 wan_ip/last_seen 2 行写（do-terminal.js:226/232）。常驻连接无感；重连风暴（最坏 3s/次）= 57,600 行读+写/天/机。可接受记录项。

- **W-L4 TerminalDO 会话缓冲理论上界**：userBuf/agentBuf 各 128 条 × 最大 1MB WS 消息 = 理论 128MB（恰为 DO 内存限）。实际被「前端按 ack 推进」协议约束（上传帧等 write_result 才发下一帧；终端输入帧极小），非滥用不可达。可顺手改为按**字节总量**（如 4MB）封顶更稳。

### 11.6 复核通过项：成本优化体系（重点确认清单）

1. **前端零轮询架构**：3s sync 已废弃（上报驱动推送），1s 定时器仅本地老化 DOM、零请求、`document.hidden` 跳过（app.js:502-511）。

9. **range 白名单**（utils.js:88-95）：拒绝任意 `\d+(h|d)` 防 `ts % step` 取模全表扫——此前 review 发现的行读放大漏洞，确认仍生效。
10. **内存 Map 全部有防无限增长清理**：authCache 1000 / syncAt 500 / apiCounts 200 / loginFails 10000 / serverListCache 500；其余 Map（serverRowCache/reportBatch/lastSeenWrite/customWritten/agents/agentInterval）键空间 = 机器数，天然有界。
11. **exec/upload pending Map 全路径清理**：超时 resolve + agent 断连 cleanup + finally（uploading Set），无泄漏。

### 13.1 High：Esc 关闭复合链——三个缺陷叠加导致编辑内容丢失

Esc 统一处理器（app.js:2082-2092）：`modals.find(第一个非 hidden)` + `open.querySelector('.modal-head button')` 模拟点击。三个缺陷：

1. **选择器命中非关闭按钮**：`querySelector('.modal-head button')` 取 DOM 第一个 button——file-editor-modal 的 head 按钮顺序是「保存/预览/扩大/取消」（index.html:129-134），**Esc = 点击「保存」**；file-selector-modal 是「移动到此处/取消」（index.html:148-149），**Esc = 确认移动**。
2. **find 取 DOM 顺序第一个而非视觉最顶层**：编辑器打开时文件管理弹窗仍在（下层）——第一次 Esc 关的是**背景的文件弹窗**（`closeFileModal` → WS 断开），编辑器还开着。
3. **saveFileEditor 不校验连接**（app.js:929-936）：WS 已断时 `upload()` 静默入队（`_sendNextUpload` 的 `if (this.connected)` 丢弃发送），无错误提示。

**完整丢失链**（用户在编辑器按两次 Esc）：关闭文件管理器（WS 断）→ 触发「保存」（绕过 dirty 二次确认）→ `closeFileEditor()` 关闭编辑器 → 上传帧因 WS 断被静默丢弃 → **改动丢失且零提示**（「保存中...」永不兑现）。选择器场景同理：Esc×2 = 关文件管理器 + 执行移动（静默失败但提示「移动中」，误导）。

**修复建议**（三处独立修，任一即可断链）：① Esc 目标按钮选择器改 `.modal-head button.icon`（所有 ✕ 关闭按钮均有 icon class，保存/移动按钮没有——一行修复）；② `modals.find` 改为取**最后一个**非 hidden（DOM 顺序 = 视觉叠放顺序，style.css 统一 z-index:10）；③ `saveFileEditor` 开头校验 `fileSess.connected`，断连时 toast 阻止关闭。三处全修最稳。

### 13.2 Medium

#### F-M1 FileSession 传输状态在 close/open 均不清理——中断后重开弹窗永久卡死

`api.js` FileSession：`close()` 只关 WS（line 65），`open()` 调 close() 后不清理 `uploadState/downloadState/editState`。场景：上传/下载进行中用户点「✕」关闭文件管理弹窗 → WS 断（传输中止）→ 重新打开文件管理 → `upload()` 命中 `if (this.uploadState)` 报「**已有上传进行中，请等待完成**」——而取消按钮（btn-file-cancel）在已关闭的弹窗里，**永久卡死直到刷新页面**；downloadState 同理报「已有下载进行中」。保存编辑器的 `upload()` 也会被同一残留挡住。同时 agent 端临时文件 `{path}.upload.{id}` 无 abort 通知（会话结束兜底清理，无害）。

**修复**：`close()` 里复位三个状态——uploadState 先发 `abort` 帧（连接还在时）再置 null，downloadState/editState 直接置 null；或 `open()` 开头复位。一行级修复 + 一个状态泄漏全消。

#### F-M2 IP 归属地隐私开关不覆盖旗帜路径

管理员关闭「IP 归属地查询（将公网 IP 发送到第三方地理服务）」后：`CfIp` 组件有 geoEnabled 守卫（utils.js:414）不查询，但**卡片旗帜路径 `updateFlags()`（app.js:357-368）直接调 `geoLookup(ip)`，其内部无 geoEnabled 检查**——每台服务器的公网 IP 仍被发送到 ipapi.co/ipwho.is，隐私开关对该路径失效（updateFlags 注释自称「geo 查询受 geoEnabled 开关控制」但代码没有）。开关文案承诺的行为与实际不符。

**修复**：`geoLookup` 入口统一检查 `geoEnabled`（关闭时直接返回 null）——旗帜随之不显示（geo 关闭时无旗帜是自洽语义），CfIp 的守卫变为冗余但无害。一处收口两个调用方。

#### F-M3 本地在线老化阈值与服务端 30s 过渡期语义冲突——后台切回闪「离线」

`agingServers` 固定 20s 阈值（app.js:301-309，快宽限 15s+5s 余量），但服务端 PanelDO 为「首观者切快采」专门设计了 **30s 过渡期慢宽限**（180s，防切快采完成前误判离线，do-panel.js:16-17）。场景：页面后台超一个慢采周期（agent 120s 一帧）→ 切回前台 → sync 推送（服务端按过渡期判 online=true，正确显示在线）→ **1s 后 updateAging 用 20s 阈值覆盖为「离线」** → agent 恢复快采首帧到达（≤10s）后变回在线。每次「后台较久后切回」必现徽章 在线→离线→在线 闪烁，服务端过渡期的良苦设计被前端老化破坏。

**修复**：收到推送后 N 秒内（如 30s）跳过老化覆盖（记录 `lastDataAt`），或老化阈值在前台恢复初期跟随慢宽限；与服务端 `fastSince` 过渡期对齐即可。

## 16. L10 升级回归事故：rustls CryptoProvider 缺失（2026-08-25 生产发现并修复）

**现象**：v2026.08.25-0737-10cb86bb 启动即崩溃——`rustls-0.23.43 panic: Could not automatically determine the process-level CryptoProvider`；`--help` 正常（不涉 TLS）。

**根因**：tungstenite/tokio-tungstenite 自 0.24 起对 rustls 声明 `default-features = false` 且**不带任何 crypto provider**（provider-agnostic 设计变更）；rustls 0.23 要求恰好启用 ring/aws-lc-rs 之一。旧 0.21 时代 tokio-tungstenite 声明 rustls **不含 default-features=false**（rustls 0.22 默认含 ring）——升级 0.21→0.30 后 provider 消失，首个真实 wss 连接时 `ClientConfig::builder()` panic。

**为何全部验证未拦截**：
1. 单元/E2E/本地演练/dev 实测**全部走 ws:// 回环**，TLS 路径从未被执行过（复现要点：连接被拒不算——TLS 连接器在 TCP 建连后才构造，必须指向有监听的端口）；
2. §9 复核时「grep Cargo.lock 确认 ring 在依赖树」的方法论错误——Cargo.lock 包含未启用的 optional 依赖，ring 在锁中不代表 rustls 的 ring feature 已启用。

**受影响 Release**（tag 逐一核对 tungstenite 版本）：`2026.08.19-1245` 至 `2026.08.25-0737-10cb86bb` 共 9 个；`2026.08.18-1332` 及更早正常。

**修复**：Cargo.toml 显式依赖 `rustls = { default-features = false, features = ["ring","std","tls12"] }`（feature 合一全局生效；选 ring 非 aws-lc-rs：后者需 cmake/nasm，musl 交叉痛苦；ring 四平台此前均已在 CI 验证——升级前 rustls 0.22 默认含 ring）。新增回归测试 `rustls_crypto_provider_compiled_in`：直接调用 `ClientConfig::builder()`（与 connect_async 同路径，无 provider 即 panic 失败）。

**验证**：本地复现（修复前同场景 panic）→ 修复后对 openssl 自签 TLS 端点得到正确的证书校验错误（`invalid peer certificate`，完整握手路径工作）；cargo 36/36（+1 回归测试）；E2E 31/31。本地交叉 check 因 ring 构建脚本需目标平台原生 C 工具链不可行——由 CI 三平台原生构建验证（历史已证明可行）。

**受影响节点恢复路径**：崩溃 agent 无法连接故不能自更新——用同目录 `.bak`（自动更新保留的上一可用版本）覆盖正式文件重启即恢复在线，再从面板更新到修复版；或手动安装修复版 Release。
